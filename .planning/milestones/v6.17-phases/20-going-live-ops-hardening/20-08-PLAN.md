<objective>
Close the two server-side MAJOR go-live gaps from Phase 20 live UAT (20-HUMAN-UAT.md `## Gaps`):

1. CORS rejects the same-origin dashboard POST (login + pause/resume) because the
   origin callback assumes same-origin requests carry no `Origin` header — true
   only for GET/HEAD. Browsers DO send `Origin` on same-origin POST, so with
   `DASHBOARD_ALLOWED_ORIGINS` empty (the shipped default) every dashboard POST
   returns 500 "CORS: origin not allowed" and the dashboard cannot log in.

2. `DASHBOARD_API_KEY` ships as the literal placeholder
   `your-secret-dashboard-api-key-here`. The bot starts on this known-default
   admin credential. For a phase whose goal is "refuses to start in any unsafe
   state," a default admin key is exactly an unsafe startup state.

Purpose: Make the dashboard control plane usable out of the box on a fresh clone
(CORS), and make the bot refuse to boot on the default admin credential (key).

Output: A same-origin-aware CORS callback that keeps the CR-02 anti-CSRF intent
intact, and a new `validateCrossEnvRules` FATAL rule for the placeholder/weak
dashboard key, plus tests.
</objective>

From src/api/server.ts (current CORS block, lines 54-71) — the EXACT code being replaced:
```typescript
const allowedOrigins = (process.env.DASHBOARD_ALLOWED_ORIGINS || '')
    .split(',').map(s => s.trim()).filter(Boolean);
app.use(cors({
    origin: (origin, cb) => {
        // Allow same-origin (no Origin header) + explicit allowlist
        if (!origin || allowedOrigins.includes(origin)) return cb(null, true);
        cb(new Error('CORS: origin not allowed'));
    },
    credentials: true,
}));
```
The `cors` package origin callback signature is `(origin: string | undefined, cb: (err: Error | null, allow?: boolean) => void)`. The `origin` arg is the request's `Origin` header value (a full origin like `http://127.0.0.1:8080`) or `undefined` when absent (GET/HEAD same-origin, curl, server-to-server).

The Express `cors` middleware does NOT give the origin callback access to the request object directly. To compare against the request `Host` header, build the middleware per-request instead of passing a static options object — see <action>.

From src/api/middleware/auth.ts — the session cookie is `sameSite: 'strict'`. This is defense-in-depth; the CORS allowlist (CR-02) is the primary cross-origin write guard. The same-origin fix must NOT weaken cross-origin rejection.

Decision logic for the origin callback (allow when ANY of these hold):
  1. No Origin header (`!origin`) → allow. Covers GET/HEAD, curl, and the
     pause/resume CLI (axios in Node sends no Origin) — unchanged behavior.

     `.host` (host:port, e.g. `127.0.0.1:8080`) to the request `Host` header
     (`req.headers.host`). If they match → allow. This is the gap fix: a
     browser POST from the SPA served BY the bot is same-origin and is NOT
     CSRF, so it must pass with zero operator config. Wrap the `new URL(origin)`
     in try/catch — a malformed Origin must fall through to rejection, not throw.
  3. Explicit allowlist: `origin` is in `DASHBOARD_ALLOWED_ORIGINS`
     (comma-split, trimmed, filtered — keep the existing parse). Covers
     cross-origin / remote dashboards the operator opts into.
Otherwise → `cb(new Error('CORS: origin not allowed'))` (unchanged rejection
path; cross-origin browser writes from a malicious page still 500, preserving
the CR-02 anti-CSRF intent).
