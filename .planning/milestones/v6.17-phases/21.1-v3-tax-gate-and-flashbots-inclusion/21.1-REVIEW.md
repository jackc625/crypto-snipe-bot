## Summary

Deep cross-file review of the three STOP-THE-LINE capital-safety fixes on a LIVE
mainnet bot (~0.009 ETH). I traced the full buy/sell submit chain
(`bot.ts` buy/exit → `txManager.sendTxWithRetry` → the three `mevStrategies/*`
→ `reconciliation.submitWithReconciliation`) and audited the tax-gate removal.

**The good news — the headline fixes are correct.** The double-spend / nonce-safe
retry rework is sound: `getTransactionCount(wallet,'latest')` is re-fetched per
attempt (`reconciliation.ts:348`), the nonce-advanced short-circuit reconciles the
prior hash without resubmitting (`:353-367`), and no `baseNonce+attempt` arithmetic
survives anywhere (grep-confirmed across `src/`). Receipt-primary reconciliation is
correct (status===1 → included / status===0 → reverted-no-resubmit / null →
nonce-corroborated window, `:259-299`), with `sawAdvancedNonce` correctly splitting
`landed-not-ours` (loud failure) from `not-landed` (escalate). The relay-accept-then-
timeout double-spend on bloXroute is closed (`nativeConfirmed:false` always +
transport-timeout deferral, `bloxroute.ts:167-182`). The `hasHighTransferTaxForChain`
removal is complete (function deleted from `tokenSafety.ts`, both V2/V3 call sites +
the import gone from `bot.ts`, dead test deleted) and `simulateHoneypotRoundtrip`
still fail-closed gates both paths BEFORE the safety bank (`bot.ts:256-283` V2 /
`:588-614` V3). Real-hash recording is wired into both V2 and V3 buy inserts
(`bot.ts:451`, `:767`). Unit tests cover all six harm-prevention assertions.

**The concern — the advertised "load-bearing" fee ceiling is bypassable on the
normal-buy path.** This is the one finding that directly falsifies a stated
acceptance invariant (review focus #3) and is filed as a BLOCKER below.

## Critical Issues

### CR-01: Affordability bound AND absolute priority-fee ceiling are bypassed on the normal buy path

**File:** `src/utils/mevStrategies/flashbots.ts:116-125`, `src/utils/mevStrategies/passthrough.ts:85-92`, `src/utils/mevStrategies/bloxroute.ts:101-103`

**Issue:**
`submitWithReconciliation` carefully computes an affordability-clamped priority fee —
`computeAffordablePriorityFee` clamps the escalated fee to `min(MEV_MAX_PRIORITY_FEE_GWEI,
affordabilityBound)`, where `affordabilityBound` is exactly the largest priority fee such
that `snipeValue + buyGasLimit×(baseFee+priorityFee) + reservedSellGas <= walletBalance`
(`reconciliation.ts:214-225`). It then hands `aff.priorityFeeWei` to the strategy as
`AttemptContext.priorityFeeWei`.

But every strategy then OVERRIDES that clamped value with the raw chain rate:

```js
// flashbots.ts:116-117 (passthrough.ts:85-86 identical; bloxroute.ts:101-103 the gasPrice analog)
const chainPriority = applyGasMultiplier(feeData.maxPriorityFeePerGas, gasMultiplier) ?? 0n;
const priorityBid = a.priorityFeeWei > chainPriority ? a.priorityFeeWei : chainPriority;
```

On a normal buy `gasMultiplier` is `undefined`, so `applyGasMultiplier` returns the fee
unchanged (`types.ts:46`) and `chainPriority === feeData.maxPriorityFeePerGas` — the
chain's *current, unclamped* priority fee straight from `getFeeData()`. The submitted
`priorityBid = max(clampedFee, chainPriority)`. Whenever the going rate exceeds the
affordability bound, the buy submits at `chainPriority`, and:

1. **The affordability reserve is defeated.** By construction `chainPriority >
   affordabilityBound` means `snipeValue + buyGasLimit×(baseFee+chainPriority) +
   reservedSellGas > walletBalance`. The buy can mine consuming the reserve that was
   meant to guarantee the exit leg can pay its gas — the exact "stranded exit" harm #5
   the bound exists to prevent.
2. **The absolute ceiling is defeated.** `chainPriority` is never clamped to
   `MEV_MAX_PRIORITY_FEE_GWEI`. `priorityBid` (and thus `maxPriorityFeePerGas`) can exceed
   the 5-gwei "Hard absolute ceiling … load-bearing safety cap" (`config.ts:171`,
   `reconciliation.ts:51`). The cap is not a cap on the actually-submitted fee.

This contradicts review focus #3 ("the ceiling is genuinely load-bearing (can't be
bypassed)") and the affordability test's own invariant
(`inclusionReconciliation.test.ts:556-558`), which only ever holds because the test asserts
on `computeAffordablePriorityFee`'s output directly — it never observes the strategy's
`max(..., chainPriority)` override. The tightest-binding regime (near-depleted wallet,
high base fee) is precisely the ~0.009-ETH funded-mainnet condition this phase is shipping
under. (Partial backstop: the Phase-20 preflight floor reserves a static
`ETH_GAS_BUFFER`=0.005 ETH (`config.ts:140`, `preflight.ts:161-163`), so a worst-case
strand is not guaranteed — but that coarse static floor is independent of priority fee and
is not the per-submit guard this phase advertises as load-bearing.)

**Fix:** Clamp the final bid to the affordability/ceiling result instead of taking the
unconditional `max` with the raw chain rate. The escalation floor should be applied
*before* the affordability clamp (i.e. compute `desiredPriorityFee = max(step×(attempt+1),
chainPriority)` and pass THAT as `desiredPriorityFeeWei` into `computeAffordablePriorityFee`),
so the clamp is the final authority:

```js
// In reconciliation.ts submitWithReconciliation, fold the going rate into the desired
// fee BEFORE clamping, and pass the chain rate through feeInputs:
const desired = feeInputs.chainPriorityWei > escalatedPriorityFeeWei
  ? feeInputs.chainPriorityWei : escalatedPriorityFeeWei;
const aff = computeAffordablePriorityFee({ desiredPriorityFeeWei: desired, /* … */ });
// strategy then uses a.priorityFeeWei DIRECTLY as maxPriorityFeePerGas — no second max():
populatedTx.maxPriorityFeePerGas = a.priorityFeeWei;
populatedTx.maxFeePerGas = baseFeeWei + a.priorityFeeWei;   // (or min(chainMaxFee, that), never larger)
```

If the going rate genuinely cannot be afforded under the reserve, `aff.affordable` then
becomes false and the buy is rejected cleanly (the intended Pitfall-7 behavior) instead of
silently overspending. Add a test that drives the *strategy* (not the pure helper) with
`feeData.maxPriorityFeePerGas` set above the affordability bound and asserts the submitted
`maxPriorityFeePerGas <= min(ceiling, bound)`.

## Warnings

### WR-01: The harmful single-chain `hasHighTransferTax` twin survives and is still imported into bot.ts

**File:** `src/utils/tokenSafety.ts:216-253`, imported at `src/bot.ts:12`

**Issue:**
The phase deleted the chain-aware `hasHighTransferTaxForChain` because it fired a
signer-connected `swapExactETHForTokens(0n, …, {value})` with NO `.staticCall` — a real
on-chain buy at uncapped slippage inside a "safety check" — then misread the
`TransactionResponse` as `bigint[]` (`taxPercent=NaN`, gate never fired). That exact
anti-pattern is still present in the **single-chain** sibling `hasHighTransferTax`
(`tokenSafety.ts:235-241`):

```js
const routerWithSigner = new Contract(CONFIG.routerAddress, ROUTER_ABI, wallet);
const actualOutput: bigint[] = await routerWithSigner.swapExactETHForTokens(   // NO .staticCall
    0n, path, walletAddress, Math.floor(Date.now()/1000)+60, { value: inputAmount }
);
```

This is a signer-connected `swapExactETHForTokens` with `{value}` and `amountOutMin=0n` and
no `.staticCall`/`callStatic` — i.e. a genuine fund-spending on-chain buy (the pattern
review focus #7 flags as CRITICAL). It is currently dead (grep confirms zero call sites: the
chain banks use the `*ForChain` functions), but it remains **exported and is still imported
by `bot.ts:12`** alongside a block of other unused single-chain helpers. The phase's own
tombstone comment (`bot.ts:27-29`) claims the harmful tax check "was deleted … (zero
callers, harmful dead code, D-ROLLBACK)" — that claim is only true for the `*ForChain`
variant; the more dangerous single-chain twin was left in place and live-imported. Per
project memory (`feedback_dont_auto_defer_confirmed_findings`), a confirmed capital-safety
landmine that a scope decision implicitly claimed to have removed should be re-surfaced, not
left filed.

**Fix:** Delete `hasHighTransferTax` from `tokenSafety.ts` (and drop it from the `bot.ts:5-14`
import) for symmetry with the `*ForChain` removal, or — at minimum — convert its real call to
`router.swapExactETHForTokens.staticCall(...)` so it can never spend funds if a future caller
wires it. Deletion is preferred (D-ROLLBACK: no re-introduction hazard).

### WR-02: D-RECORD-REAL-HASH behavioral test exercises a reimplementation, not the real bot.ts insert path

**File:** `test/unit/mevStrategies/inclusionReconciliation.test.ts:653-698` (asserting behavior of `src/bot.ts:416-462`, `:739-778`)

**Issue:**
The "buy success path records `trades.tx_hash` === real hash" behavioral test defines a
local `persistBuyRow()` helper that *reimplements* the production wiring
(`txHash: realHash ?? 'mev_bundle'`) and asserts against that copy. The real
`handleNewPairForChain` / `handleNewV3PoolForChain` insert path is verified only by a
source-grep (`:700-724`). A regression that, say, reorders the insert to write the hash
before reconciliation resolves, or reintroduces a placeholder on a branch the grep's
comment-stripping misses, would pass both tests. The grep also matches the literal
`txHash: realHash ?? 'mev_bundle'` pattern only — a refactor to `txHash: hash` (renamed var)
would silently fail the count assertion for the wrong reason. This is weaker coverage than
the test names imply, on a path whose whole point (#1 LADYS auditability) is capital-safety
relevant.

**Fix:** Add one integration test that invokes the real buy handler against a mocked
`sendTxWithRetry` (resolving a known hash) and a `insertTrade.run` spy, asserting the
persisted row carries the real hash. The existing harness in
`test/integration/txManager.test.ts` already stubs the strategy layer and can host this.

### WR-03: Affordability reserve models the buy at effective price but the tx caps maxFeePerGas higher — document the modeled-vs-cap gap

**File:** `src/utils/mevStrategies/reconciliation.ts:205-217`, `src/utils/mevStrategies/flashbots.ts:122-124`, `src/utils/mevStrategies/passthrough.ts:89-91`

**Issue:**
The affordability headroom reserves the buy cost as `buyGasLimit × (baseFee + priorityFee)`
(`reconciliation.ts:217`) — the EIP-1559 *effective* charge. But the submitted tx sets
`maxFeePerGas = max(chainMaxFee, baseFee + priorityBid)` (`flashbots.ts:124`), which under a
gas multiplier or a fee-data buffer can be materially larger than `baseFee + priorityFee`.
For most clients the *deduction* is the effective price (so the reserve math is correct for
the common case), but a wallet must hold `value + gasLimit × maxFeePerGas` for the tx to be
*accepted* by stricter mempool policies, and if the base fee rises within the block the
effective charge climbs toward the cap. Combined with CR-01 this widens the window where the
sell reserve is not actually preserved. This is a modeling gap rather than a guaranteed loss,
hence WARNING not BLOCKER.

**Fix:** When CR-01 is fixed, reserve the buy at the *submitted* `maxFeePerGas` (the value the
strategy will actually put on the tx) rather than `baseFee + priorityFee`, so the
affordability invariant matches what the node validates. At minimum, document the
effective-price assumption at `reconciliation.ts:214` so the next reader does not assume the
cap is covered.
