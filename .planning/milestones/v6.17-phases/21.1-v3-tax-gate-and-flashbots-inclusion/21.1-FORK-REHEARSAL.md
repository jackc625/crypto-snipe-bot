## 5. Anomaly diagnosis (NOT dismissed) — `antirug.http-polling.error` ×43

The fork run logged **43 error-level (`level:50`)** lines, ALL of a single op:
`antirug.http-polling.error`. Per the project "don't-dismiss-anomalies" rule and the
HONESTY REQUIREMENT, this was investigated to root cause before recording the run as a
pass:

- **What it is:** the anti-rug LP-rug **monitoring** poller (`antiRug:detector`) calling
  `eth_getLogs` with `fromBlock:0x1, toBlock:<~17M>` (an unbounded range) against
  `eth-mainnet.g.alchemy.com`, which returns **HTTP 400 Bad Request** (Alchemy rejects
  the multi-million-block range / rate-limits the backfill). The detector falls back to
  HTTP polling because the fork ChainContext has `wsProvider:null`
  (`antirug.listener.no-ws-falling-back-to-http`).
- **Why it is benign / not a failure:** it is the **position-monitoring** path
  (rug detection), entirely **separate from the buy/sell submission path** under test.
  The bot's own handler logs `"…will retry next tick"` — it is a self-healing,
  non-fatal retry by design (it does not throw, does not abort the exit loop, does not
  touch the reconciliation/nonce logic).
- **Proof it did not mask anything:** the lifecycle observables all fired regardless
  (6× passthrough TX sent + confirmed; 3× receiptDecoder `amount_out`; 3× snipe
  cooldown; antirug unregister), and all 4 fork tests PASS reading the DB `trades`
  rows. A genuine assertion failure would have produced a `FAIL` line (0 found) and a
  non-zero exit (exit was 0).
- **Provenance:** this is the SAME benign noise 21.1-03 already observed and documented
  ("Alchemy rate-limits during eth_getLogs backfill; the bot retries and all 4 fork
  tests still pass"). It is a pre-existing fork-harness artifact of the anti-rug
  backfill against a rate-limited archive RPC — **NOT** introduced by any 21.1 change
  and **NOT** on the reconciliation/tax-gate surface this phase touched. Out of scope
  (a real-fix would bound the anti-rug backfill range; tracked as harness noise, not a
  gate blocker).

## 6. Carry-forward boundary assessment — thrown-submit / double-spend (assessed, NOT dropped)

Plans 21.1-04 and 21.1-05 carried forward a boundary to confirm at this gate: the
shared `submitWithReconciliation` helper (21.1-02) has **no try/catch around the
`submit` closure** — verified directly at `src/utils/mevStrategies/reconciliation.ts`
(the call site `const result = await submit(a);` is not wrapped; a *thrown* submit
propagates straight out of the helper, bypassing helper-level reconciliation).

**Assessment: this is correctly handled and is NOT a double-spend gap.** The design
splits transport failures from explicit rejections at the strategy layer (21.1-04):

- A **transport/wait TIMEOUT** (Flashbots `wait()`=1/2, bloXroute axios timeout,
  passthrough `tx.wait` timeout) is **caught inside each strategy's `submit` closure**
  and returned as `nativeConfirmed:false` — so the helper's receipt+nonce
  reconciliation runs and returns the real hash if the tx landed. A
  **thrown-but-landed** path therefore cannot occur for these (the throw is swallowed
  and converted to deferral).
- Only a **genuine revert** (simulated-before-submit revert → never broadcast) or an
  **explicit relay rejection** (`data.error`, e.g. bad auth — the tx was never
  broadcast) is allowed to throw. In both throwing cases the tx did **not** land, so
  there is nothing to reconcile and no double-spend risk.

**Coverage that exercises this boundary (GREEN):**
- Unit `inclusionReconciliation.test.ts`: the per-strategy misreport-but-landed tests
  (timeout → deferred → reconciled → real hash, single submit) prove the
  catch-and-defer leg; the mined-but-reverted test proves the throw-on-genuine-failure
  leg; the genuine-resubmit test proves the re-fetched-nonce (no double-spend).
- Integration `mevStrategies.test.ts` / `txManager.test.ts`: `simulated-revert-never-
  broadcasts`, `relay-rejection-propagates-without-resubmit`, and the `[42,42,42]`
  re-fetched-latest assertion (replacing the old `N,N+1,N+2` double-spend assertion).
- Fork `realLaunchReplay`: the passthrough buy/sell legs land and confirm (the
  happy-path of the same closure) — the thrown-but-landed condition is structurally
  prevented because passthrough catches its own `tx.wait` timeout.

**Conclusion: the thrown-but-landed → double-spend boundary is COVERED, not a gap.**
A residual *design* observation remains (the helper itself does not reconcile a thrown
submit — it relies on the strategies to never throw on a landed-but-misreported tx). It
is documented here and was confirmed safe; if a future change wants the helper itself
to reconcile a thrown closure, that is a helper-level enhancement (flagged, not
silently deferred). This is NOT a STOP-THE-LINE finding — no capital-safety bug.
