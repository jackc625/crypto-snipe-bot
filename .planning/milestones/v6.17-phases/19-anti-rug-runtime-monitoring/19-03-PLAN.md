From src/utils/honeypot/types.ts (Phase 18 — read_first opens it):

The pattern is:
- One exported `type` declaration whose name communicates "verdict" intent (e.g., HoneypotResult).
- Each variant is a struct with a `verdict: 'safe' | 'unsafe' | 'unknown'` literal field + variant-specific evidence fields.
- The `unknown` variant carries a `reason: string` so callers can log why classification failed.
- Vacuous-pass is unrepresentable: there is no variant whose verdict is 'safe' without evidence.

RugEvaluation MUST follow this shape (per 19-PATTERNS.md §"src/anti-rug/types.ts" lines 511-545) but with one extra variant: 'allowlisted' (a destination that hit the allowlist suppresses the trigger — not 'safe' because we WANT the audit-trail of which locker, and not 'unsafe' because we explicitly chose to not exit).

From src/utils/abis.ts: existing PAIR_ABI + V3_POOL_ABI are the centralised event ABIs. PAIR_BURN_EVENT and POOL_BURN_EVENT / POOL_COLLECT_EVENT are NEW additions per 19-RESEARCH.md §1.1 + §1.2.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `ctx.httpProvider.getCode()` response | external RPC reply controls whether verifyAllowlistAtStartup proceeds — a hostile RPC that returns '0x' for a legitimate locker would cause spurious startup failure (DoS); returning non-'0x' for an EOA would silently pass an EOA into the allowlist |
| `lp_baseline` write at buy success | snapshot values flow from on-chain `getReserves` / `liquidity` into persistent storage; if RPC returns stale/manipulated values, the baseline is wrong and signal-1 false-positives become possible |
| event-decoding ABIs in events.ts | wrong ABI hash → no events match → silent monitor failure (analogous to Phase 18 Pitfall #1 vacuous-pass) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-19-03-01 | Spoofing | RPC returns '0x' for a legitimate locker contract | accept | Hostile RPC is out-of-scope for the bot's threat model (operator owns the RPC credential); if it happens, the bot refuses to start with a clear FATAL log naming the affected locker — operator escalates by switching RPC. |
| T-19-03-02 | Tampering | RPC returns stale reserves at buy success | mitigate | LP baseline is captured via `Promise.all([getReserves, totalSupply])` at the buy-success block; the multi-signal AND chain (Plan 19-04) requires ALL THREE signals to fire before exiting, so a stale baseline causing signal-1 false-positive alone does not trigger an exit. |
| T-19-03-03 | Information disclosure | log.info dump of merged allowlist at startup | accept | All addresses are public on-chain; D-LIST-VERIFY explicitly requires the dump for operator visual verification. Local-only operator UI per UI-SPEC item 1. |
| T-19-03-04 | Repudiation | allowlist verification step skipped | mitigate | Plan 19-05 wires `verifyAllowlistAtStartup` into `startMultiChainBot` BEFORE the detector listeners start; a grep-assertion in the verify gate (Plan 19-05) checks the call site exists. |
| T-19-03-05 | Denial of service | Allowlist sized in the hundreds (operator overlay) → startup time grows | accept | Each getCode is ~50ms; even 100 lockers = 5 seconds at startup. Acceptable for a manual-start ops process. The hardcoded base is 4 V2 + 4 V3 per chain × 4 chains = ~32 calls total even without overlay. |
| T-19-03-06 | Tampering | Wrong topic hash in events.ts (silent monitor failure) | mitigate | Task 1 Tests 6-9 explicitly assert each topic hash equals the runtime-computed `ethers.id(<signature>)` — catches a typo at unit-test time. |
| T-19-03-07 | Elevation of privilege | DEAD_ADDRESS check uses case-insensitive comparison | mitigate | `address.toLowerCase() === DEAD_ADDRESS` ensures both `0x000…dEaD` (mixed) and `0x000…dead` (lower) and `0x000…DEAD` (upper) all match. Tests cover the case. |
