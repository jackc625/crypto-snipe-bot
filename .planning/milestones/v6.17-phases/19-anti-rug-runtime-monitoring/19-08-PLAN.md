# Anti-Rug Rollout — Operator Handoff

This document is the authoritative reference for rolling Phase 19 anti-rug monitoring
from dry-run to live on each chain. Per D-OPERATOR-HANDOFF (CONTEXT.md) and
D-LIVE-GATE (7 calendar days dry-run minimum AND review of every observed dry-run
trigger with 0 confirmed false-positives before flipping live).

**SAFETY DEFAULT: ALL chains ship with anti-rug in DRY-RUN MODE on first deploy.**
You explicitly flip per-chain `<CHAIN>_ANTIRUG_LIVE_EXECUTE=true` in `.env` and
restart the bot to graduate a chain to live exits.

## 1. Pre-flight — Required `.env` changes

Anti-rug introduces 8 required env vars per chain (+ 1 optional = 9 per chain total). All have sensible
defaults that ship in `.env.example`; you only need to change them if you are
graduating to live mode or tuning thresholds per dry-run review.

**Per Warning 5 from plan-checker iteration 1:** The env surface grew from the 7 originally enumerated in CONTEXT.md D-ENV-EXAMPLE to 9 per chain. The additions are `<CHAIN>_ANTIRUG_BACKFILL_CAP_BLOCKS` and `<CHAIN>_ANTIRUG_MAX_BACKFILL_BLOCKS`, both required to make the WS reconnect+backfill path operable per RESEARCH CRITICAL #1 (Alchemy free-tier 10-block getLogs cap). The additions are authorized under CONTEXT.md "Claude's Discretion" on the backfill window cap.

| Env Var | Default | Description |
|---------|---------|-------------|
| `<CHAIN>_ANTIRUG_LIVE_EXECUTE` | `false` | Dry-run (true → live exit; flip only after 7-day review per D-LIVE-GATE) |
| `<CHAIN>_ANTIRUG_LP_REMOVAL_PCT` | `50` | Signal 1: % of LP removed vs baseline that trips threshold |
| `<CHAIN>_ANTIRUG_CONFIRM_BLOCKS` | `1` (ETH); per-chain | Confirm-after-N-blocks before exit fires |
| `<CHAIN>_ANTIRUG_CIRCUIT_BREAKER_TRIGGERS` | `3` | CB trips after N anti-rug exits within window |
| `<CHAIN>_ANTIRUG_CIRCUIT_BREAKER_WINDOW_HOURS` | `1` | CB rolling window in hours |
| `<CHAIN>_ANTIRUG_GAS_MULTIPLIER` | `2.0` | Multiplier on EIP-1559 fields when reason=anti-rug |
| `<CHAIN>_ANTIRUG_BACKFILL_CAP_BLOCKS` | `10` (ETH Alchemy free) / `500` (others) | Per-getLogs-call cap; **upgrade Alchemy to Pay-As-You-Go for unlimited on ETH** |
| `<CHAIN>_ANTIRUG_MAX_BACKFILL_BLOCKS` | `7200` (~1 day on ETH) | Hard ceiling; gap > this fires [GAP DETECTED] |
| `<CHAIN>_ANTIRUG_ALLOWLIST_EXTRA` | (empty) | Optional comma-separated extra V2+V3 locker checksummed addresses |

`<CHAIN>` is one of `ETH`, `BSC`, `BASE`, `ARB` (each chain has its own set of vars).

**Critical for ETH** (per 19-RESEARCH.md CRITICAL #1): Alchemy free tier caps
`eth_getLogs` at **10 blocks per query**. The default `ETH_ANTIRUG_BACKFILL_CAP_BLOCKS=10`
is set for free-tier safety. If your bot has been offline for more than a few blocks,
chunked iteration runs many small `getLogs` calls (still fine). For production live
mode, **upgrade Alchemy to Pay-As-You-Go** (unlimited per-call) and bump the cap to
2000+ via `.env`.

**Critical for all chains**: `<CHAIN>_ANTIRUG_LIVE_EXECUTE=true` is the single
on/off switch for live exits. Set strictly to the string `'true'` — any other value
(including `TRUE`, `1`, missing) defaults to `false` (dry-run) per Plan 19-02
validator strictness.

## 2. Bot restart procedure post-`.env` changes

After any `.env` change to anti-rug variables:

```bash
# 1. Stop the bot cleanly
# (Ctrl+C in the bot terminal; the bot's process should exit gracefully)

# 2. Verify .env changes
grep ANTIRUG .env

# 3. Start the bot
npx ts-node src/bot.ts

# 4. Watch the startup logs for the per-chain allowlist verification
# Look for log lines with op='antirug.allowlist-verified' or fatal 'antirug.allowlist-eoa-rejection'
```

If any allowlist address fails the `getCode()` check (per D-LIST-VERIFY), the bot

it from your `<CHAIN>_ANTIRUG_ALLOWLIST_EXTRA` env if you added it manually.

## 4. Per-chain verification protocol — live mode flip per D-LIVE-GATE

**Prerequisites (ALL required per D-LIVE-GATE):**

1. **7 calendar days minimum** in dry-run mode on this chain.
2. **Review every dry-run trigger** that fired during the window — use the dashboard
   "Anti-Rug Monitor" tile and the "Frontrun Outcome Distribution" panel.
3. **Zero confirmed false-positives** — every triggered evaluation was either a real
   rug-pull or an allowlist suppression you reviewed and accepted.

**Per-chain live flip procedure:**

```bash
# 1. Stop the bot
# (Ctrl+C; clean exit)

# 2. Edit .env — flip ONE chain at a time
# For ETH:
# Before: ETH_ANTIRUG_LIVE_EXECUTE=false
# After:  ETH_ANTIRUG_LIVE_EXECUTE=true

vim .env  # or your editor of choice

# 3. Verify the change
grep ETH_ANTIRUG_LIVE_EXECUTE .env
# Should output: ETH_ANTIRUG_LIVE_EXECUTE=true

# 4. Restart the bot

# 5. Verify live mode is active
# Dashboard: "Anti-Rug" column should now show 🟢 Live badges
# Logs: grep antirug.live bot-logs/*.log
```

**Rollback (per D-LIVE-ROLLBACK):** to revert a chain to dry-run, repeat the

The bot resumes monitoring in dry-run within ~30s of restart.

## 5. Circuit-breaker reset procedure

The circuit breaker auto-disables anti-rug for a chain after N triggers in W hours
(defaults: N=3, W=1 — per `<CHAIN>_ANTIRUG_CIRCUIT_BREAKER_TRIGGERS` and
`_WINDOW_HOURS`). When tripped, the dashboard renders a red banner at the top of
the Overview page:

> **ANTI-RUG HALTED ON ETH — 3 triggers in last hour**
> [Click to review and reset]

**Primary procedure — dashboard modal flow (per UI-SPEC):**

1. Click `Click to review and reset` link in the banner.
2. The "Review and Reset Anti-Rug Circuit Breaker — {CHAIN}" modal opens.
3. Each trigger event shows full evidence (token, pair, signals, outcome, timestamp).
4. Check the `I have reviewed this trigger` checkbox for EACH trigger (default N=3).
5. After all checkboxes are checked, the `Type RESET to confirm` input appears.
6. Type `RESET` (case-sensitive, exact match).
7. Click `Reset Circuit Breaker` to fire `POST /api/anti-rug/circuit-breaker/{chain}/reset`.
8. On success: modal closes, banner disappears, anti-rug resumes for the chain.
9. On failure: inline error rendered; the CB stays tripped; check bot logs for the cause.

**Backup procedure — CLI:**

If the dashboard is unreachable:

```bash
# Replace <CHAIN> and <API_KEY> with your values
curl -X POST \
  -H "Authorization: Bearer <API_KEY>" \
  http://localhost:3001/api/anti-rug/circuit-breaker/<CHAIN>/reset
# Success: {"ok": true, "chain": "<CHAIN>"}
# Not tripped: HTTP 409 {"error": "Circuit breaker not currently tripped on this chain"}
# Unknown chain: HTTP 404 {"error": "Chain not found"}
```

`<API_KEY>` is the `DASHBOARD_API_KEY` value from your `.env`.

**Last-resort procedure** — if all else fails and the chain must be removed from
operation pending investigation:

```bash
# 1. Stop the bot
# 2. Edit .env: remove <CHAIN> from ENABLED_CHAINS
# 3. Restart — the chain will not be initialized; anti-rug + factory listeners
#    + exit monitors all skip this chain
```

## 6. Troubleshooting common WS-disconnect / backfill-gap scenarios

### Scenario A: 🟡 Reconnecting indicator persists > 60s

**Cause:** WebSocket connection to the chain's RPC dropped; the bot is in
exponential-backoff reconnect loop (1s → 60s).

**Diagnose:** `grep 'Anti-rug WebSocket' bot-logs/*.log` — look for `disconnected,
reconnecting` and matching `reconnected, re-subscribed` lines.

**Fix:** Usually self-resolves within 60s. If persistent, check your
`<CHAIN>_WS_URL` configuration in `.env` and the RPC provider's status page
(e.g., status.alchemy.com).

### Scenario B: 🔴 Disconnected indicator > 60s

**Cause:** Reconnect failed repeatedly. Telegram alert was sent automatically per
D-VIS-WS-HEALTH.

**Fix:** Check the bot logs for `Anti-rug reconnect failed` lines + error details.
Common causes: invalid `<CHAIN>_WS_URL`, RPC provider outage, network issue.

### Scenario C: [GAP DETECTED] banner appears

**Cause:** Reconnect succeeded but the gap between `lastSeenBlock` and `currentBlock`
exceeds `<CHAIN>_ANTIRUG_MAX_BACKFILL_BLOCKS` (default 7200 = ~1 day on ETH). The
detector FAILED CLOSED per D-BACKFILL — backfill was skipped to avoid hammering
the RPC.

**Fix:**
1. Review the events on Etherscan manually for the affected block range
   (`fromBlock — toBlock` shown in the banner).
2. If no rug-pull events occurred during the gap, dismiss the banner (it persists
   in localStorage until acknowledged).
3. If a rug-pull event DID occur during the gap, manually emergency-sell via the
   dashboard `Force Sell` button on the affected position.
4. Consider increasing `<CHAIN>_ANTIRUG_MAX_BACKFILL_BLOCKS` if your downtime
   patterns regularly exceed the default.

### Scenario D: positions show 'Unmonitored' badge

**Cause:** The position was opened BEFORE Phase 19 shipped (no `lp_baseline` row),
OR the baseline snapshot failed at buy success (RPC error).

**Fix:**
- For pre-Phase-19 positions: there is no `lp_baseline` to compare against; the
  position remains unmonitored until it closes. Consider emergency-selling these
  positions if they're significant.
- For baseline-snapshot-failed positions: check the bot logs for
  `op: 'antirug.baseline-snapshot-failed'` — the position is unmonitored despite
  having an active exit monitor; either close the position manually or wait for
  the bot's standard exit monitor to fire.

# Anti-Rug Threshold Tuning — Operator Protocol

Per D-TUNE-PROTOCOL (CONTEXT.md): threshold tuning is **manual review + documented
protocol**. After the 7-day dry-run window, the operator reviews dry-run telemetry
(false positives, frontrun outcome distribution, allowlist hit rate) and adjusts
per-chain env vars based on observed behavior.

This document describes WHAT to tune and WHEN. The actual procedure for editing
`.env` and restarting the bot is documented in `docs/operations/anti-rug-rollout.md`.

## Tunable Parameters

All anti-rug thresholds are per-chain env vars with sensible defaults shipped in
`.env.example`. Tuning happens by editing `.env` and restarting.

| Env Var | Default | When to tune |
|---------|---------|--------------|
| `<CHAIN>_ANTIRUG_LP_REMOVAL_PCT` | `50` | Decrease if dry-run shows real rugs at <50% removal escaping detection (rare — legitimate operations rarely remove 40-50% in one tx). Increase if you see false positives on legitimate large-LP-rebalance transactions. |
| `<CHAIN>_ANTIRUG_CONFIRM_BLOCKS` | `1` (ETH); per-chain | Increase on reorg-volatile chains (e.g., BSC reorgs are rare but possible — 2 blocks adds safety). Decrease only if you need sub-block frontrun latency (likely never — sub-12s detection is the WS path, not the confirm-block path). |
| `<CHAIN>_ANTIRUG_CIRCUIT_BREAKER_TRIGGERS` | `3` | Increase if you have many open positions on the chain (e.g., 20+) and 3 triggers/hour represents normal operation. Decrease if 3 triggers in an hour SHOULD be enough to halt for review (the safety default). |
| `<CHAIN>_ANTIRUG_CIRCUIT_BREAKER_WINDOW_HOURS` | `1` | Increase to widen the rolling-window denominator (1 trigger/4h vs 1 trigger/1h). Decrease for stricter circuit-trip semantics. |
| `<CHAIN>_ANTIRUG_GAS_MULTIPLIER` | `2.0` | Increase during high-MEV competition periods (e.g., known rug-deployer activity). Decrease only with caution — 2.0× is the recommended frontrun-bid baseline per RESEARCH §9 frontrun racing dynamics. |
