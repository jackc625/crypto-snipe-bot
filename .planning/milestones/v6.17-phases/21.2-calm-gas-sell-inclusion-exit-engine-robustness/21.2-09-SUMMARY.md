# Phase 21.2 Plan 09: Finding B Liveness Layers (Two-Stage SIGINT + Exit-Worker Watchdog) Summary

**A funded mainnet bot that is ALWAYS killable (two-stage SIGINT replacing the single-stage gracefulShutdown — no competing force-exit timers) and never silently wedged (a Promise.race watchdog aborts any budget-overrunning submit and keeps the bot alive monitoring everything else), completing the Finding B defense-in-depth alongside 21.2-02's withTimeout layer.**

## Accomplishments
- **Two-stage SIGINT** (`createTwoStageShutdown`) fully REPLACES the old single-stage `gracefulShutdown`: the first SIGINT/SIGTERM begins graceful cleanup and arms exactly ONE `.unref()`'d force-exit timer over `SIGINT_GRACE_MS` (default 8000); a second signal forces `process.exit(130)`, the grace-timeout forces `process.exit(1)`. The old single 5s force-exit timer is gone — proven by a source grep (no `function gracefulShutdown`, no `'Force exit after 5s timeout'`).
- **Exit-worker watchdog** (`makeExitWatchdog`) bounds each serial-worker submit by `WATCHDOG_BUDGET_MS` (default 60000, must exceed one 45s confirm-window + margin) via `Promise.race`. On overrun it frees the drain loop (resolves `false`), logs `op:'watchdog.abort'` + sends a per-chain Telegram alert with a remediation pointer (D-ALERTS), and KEEPS the bot alive — the drain loop processes the next queued exit; the stuck position stays held + monitored (21.2-07) and retries on a later poll tick.
- **Proven by fake-timer unit tests:** SIGINT (5 tests) — first-graceful, second-forces-exit, grace-timeout-forces-exit, single-timer, source-grep; Watchdog (5 tests) — abort-on-overrun, no-abort-under-budget, no-timer-leak, alert+dotted-op, and bot-stays-alive (real ExitWorker: a second enqueued exit runs after the first is aborted).

## Decisions Made
- **Watchdog INSIDE the nonce lock (not outside).** `withNonceLock` chains the next op behind the prior op's settlement. Had the watchdog sat OUTSIDE the lock, a hung executor would free the drain loop but leave the hung promise as the wallet's nonce-chain tail — the next same-wallet submit would block behind it forever, so the watchdog would NOT actually keep the bot alive for same-wallet exits. Wrapping the watchdog INSIDE the lock makes the bounded submit occupy the nonce chain, so a budget abort advances the chain and the next queued exit proceeds. This was caught by the "bot stays alive" test (Test 2), which failed under the naive outside-the-lock wiring. This is RESEARCH Pitfall 6's deeper trap.
- **Watchdog in its own helper module** (`src/utils/exitWatchdog.ts`), re-exported by `bot.ts`. The plan allows "src/bot.ts (or a small helper it owns)." Keeping the watchdog out of the heavy `bot.ts` import graph (riskManager/api/telegram) makes it independently and hermetically unit-testable and reusable (D-QUALITY-FIRST). `bot.ts` still owns the `WATCHDOG_BUDGET_MS` knob + the install call.
- **Watchdog RESOLVES to a sentinel rather than throwing on overrun** — a thrown timeout would surface as a worker `submit-failed` log and muddy the survive-and-continue contract; resolving `false` is the clean "freed, keep going" signal.
- **Both env knobs parsed defensively** (never NaN/negative → fall back to default, not zero). `SIGINT_GRACE_MS` / `WATCHDOG_BUDGET_MS` were already registered in `config.ts` REQUIRED_ENV_VARS and `.env.example` by 21.2-02, so D-ENV-EXAMPLE was already satisfied — no new rows needed.
