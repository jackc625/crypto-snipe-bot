### D-AUDIT-PATH (per-host install notes)

Operator path on Windows host (this audit's run):

1. `pip install slither-analyzer` — native install OK on Windows. `solc-select` auto-installed as a transitive dep; used to download + activate solc 0.8.28.
2. `pip install mythril` — **failed** on Windows (Python 3.13) because `ckzg` and `pyethash` require MSVC `cl.exe` to build from source and no prebuilt wheels are available for 3.13. **Workaround:** use the official `mythril/myth:latest` Docker image. Mythril 0.24.8 runs cleanly inside the container.
3. **Solc-bin DNS** — the official Mythril Docker image still hardcodes `solc-bin.ethereum.org` as the solc-binaries CDN, which now NXDOMAINs (the canonical URL is `binaries.soliditylang.org`). Workaround: pre-download `solc-linux-amd64-v0.8.28+commit.7893614a` from `binaries.soliditylang.org` onto the host, bind-mount into `/home/mythril/.solcx/solc-v0.8.28` inside the container. The CI runner is Linux, so this Docker-image dance is Windows-host-only; the GitHub Actions job uses native `pip install mythril` on `ubuntu-latest`.
4. **Solc remappings via `--solc-json`** — Mythril's `--solc-args` flag does NOT forward `--allow-paths` correctly because Mythril uses `solc --standard-json` mode internally; remappings must live in the `settings.remappings` JSON. The audit run used `reports/solc-settings.json` (gitignored — see `reports/.gitkeep` preservation rule).

The CI gates (plan 18-05 Task 3, `.github/workflows/test.yml`) run on `ubuntu-latest` where `pip install mythril` works directly — this Windows-host workaround is documented for local re-runs only.

## Slither Findings (Medium+) — Disposition Table

Per RESEARCH.md lines 710-715 every medium+ finding is dispositioned below. Acceptable dispositions: `fix-applied` (with commit ref), `false-positive` (with reasoning), `accepted-risk` (with reasoning + owner sign-off). NO row in this table is `accepted-risk` — operator sign-off NOT required.

| # | Detector | Severity | Location | Disposition | Justification |
|---|----------|----------|----------|-------------|---------------|
| 1 | arbitrary-send-eth | High | `_v2Buy` — `r.swapExactETHForTokens{value: amountIn}(...)` @ HoneypotChecker.sol#144-152 | false-positive | The `router` address is a CALLER-CONTROLLED parameter to `checkV2(router, token, amountIn)`; Slither correctly flags that the destination is not constant. BUT this contract is designed to be invoked via `eth_call` (off-chain simulation only) and ALWAYS reverts at the end (`revert RoundtripResult(...)`); state is rolled back; the contract holds zero balance between calls; `msg.value` funds every invocation. The "arbitrary" recipient is by design — the caller chooses which router to simulate against. **No funds are at risk** because no funds persist. Mitigated structurally by D-CONTRACT-IMMUTABLE (no owner key, no proxy, no killSwitch). |
| 2 | arbitrary-send-eth | High | `_v3Buy` — `ISwapRouter02(swapRouter).exactInputSingle{value: amountIn}(...)` @ HoneypotChecker.sol#261-277 | false-positive | Same reasoning as #1 — `swapRouter` is a caller-controlled parameter; the eth_call + revert-always design ensures no funds persist. |
| 3 | reentrancy-balance | High | `_v2Buy` — `balBefore` at #143 read before external swap, `balAfter <= balBefore` checked at #154 | false-positive | Slither flags `balBefore` as a "stale balance used after the call." This is INTENTIONAL — the entire purpose of the lying-balanceOf catch (per plan 18-02 D-CONTRACT-SCOPE) is to compare pre-call to post-call balance. Reentrancy attack vector is also structurally impossible: (a) every invocation ends in `revert RoundtripResult(...)`, so any state mutation an attacker triggered via reentrancy is rolled back; (b) the contract is read-only by intent (called via `eth_call`); (c) the contract holds no persistent state. The `balBefore`-then-`balAfter` pattern is the documented `BUY_BAL_ZERO` check from threat T-18-03. |
| 4 | reentrancy-balance | High | `_v3Buy` — `balBefore` at #259, `balAfter - balBefore < received` at #282 | false-positive | Same reasoning as #3 — this is the V3 equivalent (`BUY_BAL_LIE` catch per threat T-18-03b). The strict-less-than check is the documented lying-balanceOf catch from plan 18-02 summary line "BUY_BAL_LIE on V3: cross-checks IERC20.balanceOf delta against router-returned amountOut". |
| 5 | incorrect-equality | Medium | `_v3Sell` — `wethReceived == 0` @ HoneypotChecker.sol#348 | false-positive | Slither's `incorrect-equality` detector flags strict equality on balance-derived values as dangerous (typical example: `balance == X` allowing attackers to make `balance != X` trivially). Here the strict equality is the CORRECT semantic — the contract needs to revert ONLY when `wethReceived == 0` (the documented `V3_SELL_WETH_ZERO` catch from threat T-18-04b). Any non-zero amount is a successful sell. A range check (`< 1`, `< someThreshold`) would be wrong because the contract reverts the entire roundtrip downstream anyway and tax-bps math handles small amounts. |
| 6 | uninitialized-local | Medium | `_v3Buy.expectedTokensOut` @ HoneypotChecker.sol#243 | false-positive | The variable is declared at the top of `_v3Buy`, then assigned inside `try IQuoterV2(quoter).quoteExactInputSingle(...) returns (uint256 amountOut, ...) { expectedTokensOut = amountOut; } catch { revert QuoteFailed("buy-quote-failed"); }`. The catch branch **always reverts**, so any code path that reaches the subsequent use of `expectedTokensOut` MUST have come through the try-success branch where it was assigned. Slither's flow analysis does not follow `revert`-always patterns. Compile-validated by `npx hardhat compile` exiting 0 in plan 18-02. |
| 7 | uninitialized-local | Medium | `_v3Sell.expectedEthOut` @ HoneypotChecker.sol#307 | false-positive | Same reasoning as #6 — sell-side equivalent. The try block assigns inside the returns-destructure; the catch always reverts (`QuoteFailed("sell-quote-failed")`). |
| 8 | unused-return | Medium | `_v2Buy` ignores return of `r.swapExactETHForTokens{value: amountIn}(...)` @ #144-152 | false-positive | The V2 swap returns `uint[] memory amounts` (path-element-by-element). The contract intentionally ignores this and reads the actual ERC20 balance delta via `IERC20(token).balanceOf(address(this))` instead — this is the lying-balanceOf catch (a router returning a fake `amounts[]` cannot fool the post-trade balance assertion). Per plan 18-02 design and threat T-18-03 mitigation. |
| 9 | unused-return | Medium | `_v2Sell` ignores return of `IERC20(token).approve(router, received)` @ #173 | false-positive | Standard ERC20 approve pattern — `approve` returns `bool` for legacy reasons, but tokens that fail to approve will revert in the subsequent swap call with `INSUFFICIENT_ALLOWANCE` (or the analogous error string). The contract is in revert-always mode, so the revert propagates cleanly into the caller via `SellFailed(...)`. Mainstream defensive pattern (OpenZeppelin's `SafeERC20.safeApprove` checks the return, but this requires importing SafeERC20 which expands the audit surface — the swap-call-reverts-on-bad-approve fallback is sufficient for an eth_call-only contract). |
| 10 | unused-return | Medium | `_v3Buy` ignores return of `IQuoterV2(quoter).quoteExactInputSingle(...)` @ #244-256 | false-positive | The contract DOES read the return — `returns (uint256 amountOut, uint160, uint32, uint256) { expectedTokensOut = amountOut; }`. Slither's flow analysis cannot follow try-catch return destructuring; this is a known Slither limitation (https://github.com/crytic/slither/issues — flow-sensitive checks miss try-catch returns). Manual code review confirms `expectedTokensOut` is assigned from `amountOut` then used at #290-291. |
| 11 | unused-return | Medium | `_v3Sell` ignores return of `IQuoterV2(quoter).quoteExactInputSingle(...)` @ #308-320 | false-positive | Same as #10 — sell-side quote return is destructured into `expectedEthOut` and used at #353-355. |
| 12 | unused-return | Medium | `_v3Sell` ignores return of `IERC20(token).approve(swapRouter, received)` @ #323 | false-positive | Same reasoning as #9 — bad approve cascades to the subsequent swap revert. |
| 13 | unused-return | Medium | `_v3Sell` ignores return of `ISwapRouter02(swapRouter).exactInputSingle(...)` @ #325-341 | false-positive | The V3 sell-side swap returns `amountOut`; the contract instead reads `IWETH(weth).balanceOf(address(this))` for the `V3_SELL_WETH_ZERO` assertion (same lying-balanceOf logic as #8 but for V3 sells). This is the documented sell-side success signal per plan 18-02 summary line "V3 SwapRouter02 returns WETH (not native ETH) to the recipient... The V3 sell-side assertion checks IWETH(weth).balanceOf(address(this)) == 0 instead of address(this).balance". |

## Stop-the-Line Determination

Per `18-CONTEXT.md` **D-STOP-THE-LINE** (lines 165-172):

> If the HONEY-11 audit OR a Phase 18 regression test reveals a production bug worse than the V2/V3 sell-sim ones (e.g., a gate that grants buys when it shouldn't), the bug BLOCKS Phase 18 close.

Severity assessment of the audit findings:

- **Mythril:** 0 issues. Symbolic execution converged within the 300s / 30-depth budget across both `checkV2` and `checkV3` entry points. No exploitable paths discovered.
- **Slither High findings (`arbitrary-send-eth` + `reentrancy-balance` x2 each):** dispositioned `false-positive` because the contract operates ONLY via `eth_call` and ALWAYS reverts at the end. The eth_call + revert-always design means: (a) no state persists between invocations, (b) no funds are at risk because the contract is funded by `msg.value` per-call and reverts, (c) the "arbitrary" recipient flag is by design — the simulator caller picks the router/quoter.
- **Slither Medium findings (9):** dispositioned `false-positive`. The `unused-return` flags map onto the documented lying-balanceOf catch design (preferring real balance delta over router-returned values). The `uninitialized-local` flags are catch-always-reverts pattern flow-sense limitations. The `incorrect-equality` flag is the documented `V3_SELL_WETH_ZERO` catch.
- **Comparison to the V2/V3 sell-sim bugs:** the V2 sell-sim (`simulateSellForChain` `balance=0` hard-block) failed-CLOSED (blocked every snipe, opportunity cost only). The V3 sell-sim (`simulateSellV3ForChain` vacuous-pass) failed-OPEN (granted every buy, real-money loss possible). The HoneypotChecker contract:
  - DOES detect lying-balanceOf (threat T-18-03 mitigated via `BUY_BAL_ZERO` revert at HoneypotChecker.sol#155).
  - DOES detect silent-zero-ETH-on-sell (threat T-18-04 mitigated via `SELL_ETH_ZERO` revert at #193).
  - DOES detect V3 lying-balanceOf (threat T-18-03b mitigated via `BUY_BAL_LIE` revert at #283).
  - DOES detect V3 silent-zero-WETH-on-sell (threat T-18-04b mitigated via `V3_SELL_WETH_ZERO` revert at #349).
  - Per plan 18-02 summary, all four threats are verified by grep on the contract source.

NO finding (Slither or Mythril) reveals a path where the contract would grant a `safe` verdict for a token that should be `unsafe`. The audit is strictly more rigorous than the V2/V3 sell-sim bugs called out in D-STOP-THE-LINE.

Per RESEARCH.md lines 710-715, the three acceptable dispositions for any medium+ Slither/Mythril finding are:

| Disposition | When to use | Required artifacts |
|-------------|-------------|--------------------|
| `fix-applied` | Code change committed that addresses the finding | Commit ref (hex SHA) in the Justification cell, plus a re-run of Slither + Mythril confirming the finding is gone |
