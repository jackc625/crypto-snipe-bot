## Flashbots Inclusion Reconciliation (STOP-THE-LINE-02 — the critical fix)

### Research Q1 — `FlashbotsBundleResolution` enum + `bundle.wait()` semantics

`[VERIFIED: node_modules/@flashbots/ethers-provider-bundle/build/index.d.ts:5-9]` — package version `1.0.0`:

```ts
export declare enum FlashbotsBundleResolution {
    BundleIncluded = 0,
    BlockPassedWithoutInclusion = 1,
    AccountNonceTooHigh = 2
}
```

`wait: () => Promise<FlashbotsBundleResolution>` `[VERIFIED: index.d.ts:43]`.

**What `wait()` actually does and when it resolves** `[CITED: github.com/flashbots/ethers-provider-flashbots-bundle/blob/master/src/index.ts — waitForBundleInclusion]`:
- It polls block-by-block. **While `blockNumber < targetBlockNumber`**: it re-checks each bundle tx's account nonce; if any submitted nonce is *already consumed* (on-chain nonce advanced past it) it resolves **`AccountNonceTooHigh (2)`**.
- **When `blockNumber >= targetBlockNumber`**: it fetches `getBlock(targetBlockNumber)` and checks whether *every* `bundleTransactions[i].hash` is present in **that specific block**. If yes → `BundleIncluded (0)`; if no → `BlockPassedWithoutInclusion (1)`.
- It rejects with "Timed out" after `TIMEOUT_MS = 5 minutes`.

**Why this is the LADYS root cause (load-bearing):** `wait()` only inspects the *single* target block. If the bundle's tx mined **one block late** (the live log shows 4 sequential "not included" blocks `25182797..25182800` then the tx actually landed) or was included via a different builder path, `wait()` returns `BlockPassedWithoutInclusion (1)` **even though the tx is on-chain**. The current code (`flashbots.ts:91,114`) treats anything `!== 0` as failure and throws. `AccountNonceTooHigh (2)` is an even *more* direct "the tx already landed" signal that the code also mis-handles as failure. **Confirmed:** `[CITED: docs.flashbots.net/flashbots-auction/advanced/troubleshooting]` — "Flashbots prevents failed transactions from appearing on the chain," and block explorers are unreliable for Flashbots txs; therefore the *receipt* must be checked directly.

### Research Q2 — Is `bundleTransactions[0].hash` deterministic & computable before inclusion?

**YES.** `[VERIFIED: index.d.ts:35-43]`:

```ts
export interface TransactionAccountNonce {
    hash: string;
    signedTransaction: string;
    account: string;
    nonce: number;          // ← the submitted nonce, available directly
}
export interface FlashbotsTransactionResponse {
    bundleTransactions: Array<TransactionAccountNonce>;
    wait: () => Promise<FlashbotsBundleResolution>;
    simulate: () => Promise<SimulationResponse>;
    receipts: () => Promise<Array<TransactionReceipt>>;
    bundleHash: string;
}
```

`bundleTransactions[0].hash` is the keccak256 of the **signed raw transaction**, computed at `sendBundle` time — it is fixed and block-independent. So `provider.getTransactionReceipt(bundleTransactions[0].hash)` is a valid reconciliation probe regardless of whether `wait()` claims inclusion. **Bonus:** `bundleTransactions[0].nonce` gives the exact submitted nonce directly (no need to track `baseNonce+attempt` separately) — useful for the off-by-one guard.

> Note: the existing code at `flashbots.ts:97-100` already extracts `bundle.bundleTransactions?.[0]?.hash` on the success path and throws if missing. The reconciliation path can reuse that same extraction *before* deciding failure.

### Research Q3 — ethers v6 semantics the reconciliation depends on

All `[VERIFIED: node_modules/ethers/lib.commonjs/providers/provider.d.ts]`:

| Method | Signature | Behavior |
|--------|-----------|----------|
| `getTransactionReceipt` | `getTransactionReceipt(hash: string): Promise<null \| TransactionReceipt>` (`:1192`) | Returns **`null`** for a not-yet-mined / nonexistent tx; a `TransactionReceipt` once mined. |
| `getTransactionCount` | `getTransactionCount(address: AddressLike, blockTag?: BlockTag): Promise<number>` (`:1139`) | `'latest'` = count of mined txs (proves consumption); `'pending'` = includes mempool. |
| `waitForTransaction` | `waitForTransaction(hash: string, confirms?: number, timeout?: number): Promise<null \| TransactionReceipt>` (`:1221`) | Bounded poll; returns **`null`** on timeout, receipt on confirmation. |
| `TransactionReceipt.status` | `readonly status: null \| number` (`:635-641`) | **`1`** = success, **`0`** = reverted. |

**Which nonce blockTag proves "consumed/mined": `'latest'`.** `getTransactionCount(wallet, 'latest')` counts only mined transactions. CONTEXT.md (D-NONCE-SAFE-RETRY, D-RECONCILE-RECEIPT) locks `'latest'` — correct: `'pending'` would count an unmined replacement and give a false "advanced" reading.

### Research Q4 — D-CONFIRM-WINDOW: how to poll for a bounded window

The bot's reconciliation provider is `ctx.httpProvider`, a **`JsonRpcProvider`** `[VERIFIED: chainRegistry.ts:110-111]` (`wsProvider` is a *separate* `WebSocketProvider|null`; the reconciliation path does **not** use WebSockets, so there is **no** `WebSocketProvider` reconnect gotcha here). `getProvider` constructs it with `new ethers.JsonRpcProvider(url)` and **no** custom polling interval `[VERIFIED: src/utils/provider.ts:23]` (ethers v6 default `pollingInterval` ≈ 4000ms).

**Recommended pattern (manual bounded poll — preferred over `waitForTransaction` for this case):**
```ts
// pseudocode — runs ONLY after wait() returned non-zero and the immediate
// receipt probe was null. Polls receipt-primary, nonce-corroborating.
const deadline = Date.now() + confirmWindowMs;     // generous default below
while (Date.now() < deadline) {
  const receipt = await provider.getTransactionReceipt(signedTxHash);
  if (receipt) {                                   // mined (status 1 or 0)
    return receipt;                                // caller decides incl/revert
  }
  const latestNonce = await provider.getTransactionCount(wallet.address, 'latest');
  if (latestNonce > submittedNonce) {
    // nonce consumed but receipt not yet visible — keep polling for the receipt
    // (do NOT submit anything); receipt should appear within propagation lag.
  }
  await sleep(pollIntervalMs);                     // ~3-4s, ≈ block cadence on ETH
}
return null;                                       // genuinely not landed → escalate/fail
```

**Why manual loop over `provider.waitForTransaction(hash, confirms, timeout)`:** `waitForTransaction` keys *only* on the receipt and returns `null` on timeout; it does **not** surface the corroborating nonce signal, and CONTEXT.md wants both (receipt-primary, nonce-corroborating). A manual loop also lets us log a single structured `op:` line per poll outcome (D-ALERTS / D-04). Either is acceptable per D-QUALITY-FIRST; the manual loop is higher-fidelity for this two-signal reconciliation. **Gotcha:** the loop's poll interval should be its own value (≈3-4s), not coupled to the provider's internal `pollingInterval`; do not assume sub-second polling.

**Generous default (recommendation, within "Claude's Discretion"):** `MEV_CONFIRM_WINDOW_MS = 45000` (45s ≈ ~3-4 ETH blocks at 12s). CONTEXT.md says thoroughness beats speed; 45s gives late-inclusion ample room while bounding the buy latency. Poll interval `MEV_CONFIRM_POLL_MS = 4000`.

### Research Q5 — D-NONCE-SAFE-RETRY: the off-by-one, spelled out

Let **N = the nonce we submitted on this attempt** (available as `bundleTransactions[0].nonce` for Flashbots, or the value we set for bloXroute/passthrough). After `wait()`/relay/`tx.wait` reports non-success, read `latest = getTransactionCount(wallet, 'latest')`:

| Condition | Meaning | Action |
|-----------|---------|--------|
| `latest === N` | Our nonce is **not yet mined** (count is the index of the *next* unused nonce; if `latest === N` then nonce `N` has not been consumed). | The tx with nonce `N` did **not** land. Safe to reconcile-by-receipt one more time, then escalate/resubmit at nonce `N` (same nonce!) with a higher fee — OR fail if ceiling hit. |
| `latest > N` | Nonce `N` (and possibly more) **has been consumed** → **something landed**. | **STOP. Do NOT submit.** Reconcile: fetch `getTransactionReceipt(signedTxHash)`. If receipt `status===1` → return real hash (success). If receipt `status===0` → genuine revert failure. If receipt `null` but `latest > N` → our tx hash isn't the one that consumed the nonce (rare: a manual/competing tx); treat as "landed-but-not-ours" → fail loudly with D-ALERTS (do not retry — a new submit would use `latest` and double-act). |
| `latest < N` | Should be impossible (we submitted `N = latest_at_submit + 0` per the new scheme). | Defensive: log anomaly (per "don't dismiss anomalies" memory), treat as not-landed. |

**Critical correction to the current code:** today every attempt uses `nonce: baseNonce + attempt` (`flashbots.ts:65`, `bloxroute.ts:72`, `passthrough.ts:41`) where `baseNonce` is fetched **once** before the loop (`flashbots.ts:52`, `bloxroute.ts:61`, `passthrough.ts:33`). The new scheme: **re-fetch `getTransactionCount(wallet,'latest')` at the start of each attempt** and use *that* as the nonce. If it advanced beyond the previous attempt's nonce, the previous attempt landed → stop & reconcile. A genuine resubmit reuses the **same** current nonce (a replacement tx), not an incremented one — incrementing is exactly what risks the second real buy.

### Research Q7 — D-FEE-ESCALATION + affordability bound

**How `applyGasMultiplier` currently works** `[VERIFIED: types.ts:44-48]`:
```ts
export function applyGasMultiplier(fee, gasMultiplier) {
  if (fee === null || fee === undefined) return fee;
  if (gasMultiplier === undefined || gasMultiplier === 1) return fee;
  return fee * BigInt(Math.round(gasMultiplier * 100)) / 100n;   // fractional-safe bigint
}
```
All three strategies branch EIP-1559 vs legacy on `feeData.maxFeePerGas` `[VERIFIED: flashbots.ts:61-78, passthrough.ts:48-53, bloxroute.ts:66-67 (legacy-only on BSC)]`. `FeeData` shape `[VERIFIED: provider.d.ts:26-58]`: `{ gasPrice: null|bigint, maxFeePerGas: null|bigint, maxPriorityFeePerGas: null|bigint }`. ETH chain template is `gas: { type: 'eip1559', multiplier: 1.2, maxGasLimit: 300_000n }` `[VERIFIED: chainRegistry.ts:204]`.

**Per-retry escalation:** bump `maxPriorityFeePerGas` (not `maxFeePerGas` base) by a per-attempt step until the ceiling. A clean approach: pass an escalating multiplier into the existing `applyGasMultiplier` on `maxPriorityFeePerGas` per attempt, OR add an absolute-gwei step. Either way it must respect the hard ceiling.

**Affordability-bound math (the load-bearing safety mechanism).** The preflight wallet floor is `[VERIFIED: src/preflight.ts:161-163]`:
```
floor = parseEther(snipeAmount) × MAX_OPEN_POSITIONS + parseEther(gasBuffer)
```
The fee ceiling must guarantee that *after* this buy, the wallet still holds enough to pay the eventual **sell** gas (the whole D-FEE-ESCALATION justification is the exit leg). Recommended ceiling:
```
maxPriorityFeeCeiling = min(
  parseUnits(MEV_MAX_PRIORITY_FEE_GWEI, 'gwei'),                 // absolute cap (operator)
  affordabilityBound
)
affordabilityBound such that:
  snipeValue + (buyGasLimit × (baseFee + priorityFee))          // this buy's max cost
  + reservedSellGas                                              // MUST remain after
  ≤ walletBalance
where reservedSellGas = sellGasLimit × (baseFee × sellGasBuffer + priorityFeeCeiling)
  sellGasLimit = ctx.chain.gas.maxGasLimit (300_000n on ETH)
```
The planner computes `walletBalance = await provider.getBalance(wallet.address)`, reads `baseFee` from `feeData`, and `buyGasLimit`/`sellGasLimit` from `ctx.chain.gas.maxGasLimit` + the tx's `gasLimit`. ## Common Pitfalls

### Pitfall 1: Treating `bundle.wait() !== 0` as proof-of-failure (the LADYS bug itself)
**What goes wrong:** `BlockPassedWithoutInclusion(1)` and `AccountNonceTooHigh(2)` can both occur while the tx is on-chain (late inclusion / nonce already consumed). **Why:** `wait()` only inspects the single target block `[CITED: flashbots src/index.ts]`. **Avoid:** always reconcile against `getTransactionReceipt(signedTxHash)` + `getTransactionCount('latest')` before declaring failure. **Warning sign:** a "TX failed" log immediately followed by a balance/token change on-chain (the D-OP-DB-TRUTH check that caught LADYS).

### Pitfall 2: `baseNonce + attempt` double-spend
**What goes wrong:** if attempt-0 lands but is misreported, attempt-1 submits at `base+1` → a **second real buy**. **Why:** the nonce is fetched once (`flashbots.ts:52`) and blindly incremented. **Avoid:** re-fetch `'latest'` each attempt; stop if it advanced; resubmit (if genuinely not landed) at the *same* current nonce, not an incremented one. **Warning sign:** two `trades` buy rows for one snipe, or a wallet balance drop ≈ 2× snipe amount.

### Pitfall 3: Writing `.callStatic` (v5) instead of `.staticCall` (v6)
**What goes wrong:** `test/unit/ethersV5PatternsAbsent.test.ts:52-54` fails the build (`/\.callStatic\./` is banned). **Why:** CONTEXT.md uses "callStatic" loosely. **Avoid:** use ethers v6 `contract.method.staticCall(...)` `[VERIFIED: contract/types.d.ts:112]`. The same test also bans `BigNumber`, `ethers.providers.`, `@ethersproject/`.

### Pitfall 4: Forgetting `mockReset:true` re-registration in unit tests
**What goes wrong:** mocks return `undefined` mid-suite → "create is not a function". **Why:** `vitest.config.ts:16` `mockReset:true` wipes impls. **Avoid:** re-establish every mock impl in `beforeEach` `[VERIFIED: flashbotsBundleHash.test.ts:73-89]`.

### Pitfall 5: Confirm-window blowing the 5s unit-test timeout
**What goes wrong:** a 45s real default × poll loop hangs unit tests (`testTimeout:5000`). **Why:** the window is generous for production. **Avoid:** inject tiny `confirmWindowMs`/`pollMs` (e.g. 50ms/10ms) in unit tests, or mock the sleep; the production default lives only in config.

### Pitfall 7: Escalating fee without reserving sell gas
**What goes wrong:** a buy succeeds at a high priority fee that leaves too little ETH to ever submit the exit sell → stranded position (the exact harm D-FEE-ESCALATION exists to prevent). **Why:** the ceiling is the only thing standing between escalation and an unsellable position. **Avoid:** the affordability bound MUST reserve `sellGasLimit × fee` (§Q7); fail cleanly if even attempt-0 can't afford the reserve.

### Harm-Prevention Assertions (the minimal set that proves these bug classes cannot regress)
1. **False-negative-loses-position harm:** Given any strategy whose native confirm reports failure WHILE `getTransactionReceipt(signedTxHash).status===1` (and/or `getTransactionCount('latest')` advanced) → `sendTransaction` **resolves with the real hash** (does NOT throw). Asserted per-strategy (Flashbots/bloXroute/passthrough).
2. **Double-spend harm:** In the misreport-but-landed case, the submit primitive (`sendBundle`/`axios.post`/`wallet.sendTransaction`) is called **exactly once** (`toHaveBeenCalledTimes(1)`); on a genuine resubmit, the captured tx `nonce` equals the re-fetched `'latest'`, never `base+attempt`.
3. **V3-always-blocked harm:** A benign V3 token reaches the buy (`countTrades buy >= 1` on fork) AND a high-tax/honeypot V3 fixture still yields `verdict!=='safe'` (`countTrades buy === 0`); the removed `hasTax` field no longer gates.
4. **Mined-but-reverted false-success harm:** `receipt.status===0` → `sendTransaction` **throws** and does NOT resubmit the same nonce (prevents treating a reverted tx as a successful buy).
5. **Stranded-exit harm (D-FEE-ESCALATION):** the fee ceiling clamps so that `walletBalance - buyMaxCost - reservedSellGas >= 0`; if attempt-0 can't afford the reserve, `sendTransaction` fails cleanly (asserted via a balance-too-low fixture) rather than submitting an unsellable buy.
