# Phase 21.1: V3-Buy Tax-Gate + Flashbots Inclusion Fix - Context

**Gathered:** 2026-05-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Fix the two STOP-THE-LINE blockers that halt the Phase 21 live-capture work, on
a bot funded with ~0.009 ETH on **live mainnet**:

1. **STOP-THE-LINE-01 (V3-buy tax-gate, HIGH):** every Uniswap V3 buy aborts
   because `bot.ts:610` routes the V3 SwapRouter into the V2-only
   `hasHighTransferTaxForChain` (`tokenSafety.ts:482`), which reverts and
   fail-closes `hasTax=true`. The funded bot cannot snipe any V3 token.
2. **STOP-THE-LINE-02 (Flashbots false-negative inclusion, CRITICAL):**
   `FlashbotsMevStrategy.sendTransaction` treats any non-`BundleIncluded`
   `bundle.wait()` as failure and throws — so a buy/sell that actually landed
   on-chain is reported failed → trade never recorded, position never
   registered/monitored (untracked funds). The retry loop's `baseNonce+attempt`
   also permits a double-spend. Surfaced live by the LADYS buy (751M LADYS
   received, bot logged "TX failed").

**Scope anchor:** fix these two bug classes so the 21-07 real-capital roundtrip
can proceed. NOT new exit/snipe behavior, NOT contract deploys, NOT multi-chain
capture. The two diagnosis docs (canonical refs) are authoritative on root cause
and affected files.

**Real-capital context (verified live 2026-05-26):** wallet
`0x46c6D387EAb1669307c33E6f60173ADEe9Da3A5C`, ~0.009 ETH; `npm run preflight`
passes all 6 ETH checks. The untracked LADYS was already recovered to ETH via a
direct non-Flashbots sell (`scripts/recover-sell-ladys.ts`, tx
`0x424ed3e4ea2e81093694ecb7dafa301aa4184e696f59e80e430b72e786cc26c7`).

### V3 tax-gate fix (STOP-THE-LINE-01)
- **D-V3-TAX-REMOVE:** **Remove** the `hasHighTransferTaxForChain` call from the
  V3 safety bank (`bot.ts:607-613`, the `Promise.all` entry at `:610`) and clean
  up the downstream `hasTax` references in the V3 gate (`bot.ts:638-639` log +
  reject). Rationale (verified): `simulateHoneypotRoundtrip` runs on the V3 path
  at `bot.ts:566` **before** the safety bank, does a real on-chain buy+sell
  roundtrip, and **already enforces** `maxBuyTaxBps`/`maxSellTaxBps` with a
  fail-closed `verdict:'unsafe'` (HONEY-09, `honeypot/checkerContract.ts:31-33,
  186, 209`). The V2-style check is therefore redundant AND broken on V3. A
  QuoterV2 quote-ratio alternative was rejected: a quote ratio cannot detect real
  transfer tax (only an actual roundtrip can), so it would false-block legit
  tokens while catching nothing the roundtrip misses — lower quality and less
  safe per D-QUALITY-FIRST.
- **D-V2-TAX-REMOVE (added 2026-05-26 — owner decision; STOP-THE-LINE-03):**
  **Remove** the `hasHighTransferTaxForChain` call from the **V2** safety bank
  (`bot.ts:303`) and clean up its `hasTax` consumers — the exact mirror of
  D-V3-TAX-REMOVE. Rationale (verified): `simulateHoneypotRoundtrip` runs on the
  V2 path at `bot.ts:253` **before** the bank and already enforces buy+sell tax
  fail-closed (HONEY-07), so the call is redundant; AND it is actively harmful —
  `tokenSafety.ts:495-503` is a **signer-connected `swapExactETHForTokens(0n, …,
  {value: snipeAmount})` with no `.staticCall`**, i.e. a **real on-chain buy at
  `amountOutMin=0`** on every V2 snipe, whose result (`TransactionResponse`) is
  then misread as a `bigint[]` so `taxPercent=NaN` → returns `false` (broken tax
  math). This fires on the **21-07 capture path** (a V2 token), so it is a
  real-capital hazard that must be fixed before the capture. The fix is the same
  safe removal as V3; scope is **only the broken tax call** — the `:253`
  roundtrip and the rest of the V2 capture flow stay untouched. ALSO audit the
  sibling bank functions (esp. `simulateSwapForChain`, `bot.ts:302`) for the same
  missing-`.staticCall` real-tx pattern; any further real-submit found is a fresh
  STOP-THE-LINE escalation (do NOT fix-in-flight).
- **D-V3-ONLY-SCOPE:** Fix the V3 path in 21.1. The V2 tax call
  (`bot.ts:303`) is the path the 21-07 capture runs through and the original
  diagnosis said it "works" — do not perturb the real-capital path in an urgent
  unblock. The V2 redundancy + signer-swap anomaly were flagged for research and
  initially deferred.
  - **AMENDED 2026-05-26 (owner decision):** this fence is **partially lifted.**
    Research CONFIRMED the "V2 path works" premise was FALSE (the tax call fires a
    real `amountOutMin=0` buy with broken math — see D-V2-TAX-REMOVE), so the V2
    tax-call removal is now **IN scope as STOP-THE-LINE-03.** The fence still holds
    for the *rest* of the V2 capture flow — only the broken tax call is removed;
    the honeypot roundtrip, buy/sell submit, and exit path are untouched.
- **D-V3-FIXTURE (locked by SC1):** Flip

### Inclusion reconciliation (STOP-THE-LINE-02, SC2)
- **D-RECONCILE-RECEIPT:** When `bundle.wait()` returns non-zero
  (`flashbots.ts:114`), do **not** throw. Reconcile against chain state,
  receipt-primary: fetch `getTransactionReceipt(bundleTransactions[0].hash)`
  (the signed-tx hash is deterministic regardless of "inclusion"):
  - receipt exists && `status===1` → **included**; return that real hash so the
    trade is recorded, position registered, exit monitor started.
  - receipt exists && `status===0` → **mined-but-reverted = genuine failure**;
    do NOT retry the same nonce.
  - receipt `null` → fall through to the nonce check (D-NONCE-SAFE-RETRY).
  The on-chain nonce (`getTransactionCount(wallet,'latest')`) is the cheap
  corroborating signal and the primary driver of the retry guard.
- **D-CONFIRM-WINDOW:** Before declaring genuine "not landed", **poll
  receipt+nonce for a bounded window (~2-3 blocks / ~30s)** to absorb
  receipt/propagation lag and late inclusion. The window is a **tunable env var**
  (D-ENV-EXAMPLE) with a deliberately **generous default** (per D-QUALITY-FIRST,
  thoroughness beats speed where they conflict).

### Retry & nonce-safety (STOP-THE-LINE-02, SC3)
- **D-NONCE-SAFE-RETRY:** Replace `baseNonce + attempt` with a per-attempt
  re-fetch of `getTransactionCount(wallet,'latest')`. At the start of each
  attempt, if the nonce has advanced past the nonce we submitted, **stop and
  reconcile** (something landed) rather than submit a new tx — so a
  misreported-but-landed attempt-0 can never trigger a second real buy. A
  regression test must prove no double-spend.
- **D-SIMULATE-BEFORE-SUBMIT:** Simulate each attempt before submitting
  (`callStatic` / `eth_callBundle`) so we never escalate-and-resubmit a tx that
  would revert — reuses the existing buy/safety callStatic pattern + Phase 21's
  simulate-before-submit lineage.
- **D-FEE-ESCALATION:** For a *genuinely* not-included bundle, **escalate
  `maxPriorityFeePerGas` per retry, bounded by a HARD ceiling** =
  `min(configured absolute max gwei, an affordability bound that always reserves
  enough gas for the eventual sell)`, tunable via env (D-ENV-EXAMPLE). The
  ceiling is the load-bearing safety mechanism. Once hit, **fail cleanly** with
  D-ALERTS (structured pino + Telegram + remediation pointer). Rationale: a
  bundle that actually lands is higher-quality than one needing a manual rerun,
  and reliable inclusion is itself a *safety* property for the **sell/exit leg**
  (`executeFullSell`) that inherits this path — a sell that fails to include
  strands a position (anti-rug exits especially). Chosen over "fail cleanly, no
  escalation" via D-QUALITY-FIRST.

### Fix blast radius
- **D-SHARED-HELPER:** Extract a **shared nonce-safe-retry +
  inclusion-reconciliation helper** (home it alongside the `MevStrategy`
  interface, e.g. `src/utils/mevStrategies/types.ts` or a new sibling module —
  planner's call) and apply it to **all three** strategies. The
  double-spend/false-negative class is bot-wide, not Flashbots-only (verified):
  - `flashbots.ts` — `wait()===0`-only success + `baseNonce+attempt` (most acute;
    `wait()` actively lies).
  - `bloxroute.ts:72` — `baseNonce+attempt`; returns the relay hash at `:95`
    *without confirming inclusion*; an axios timeout after relay-accept throws →
    retry → double-spend / untracked on BSC.
  - `passthrough.ts:41` — `baseNonce+attempt`; `tx.wait(3)` timeout under RPC lag
    throws → retry → same risk on Base/Arb.
  One place to get it right; eliminates the class everywhere.
- **D-DELETE-LEGACY:** **Delete** the dead legacy `sendTxWithRetry` Flashbots
  branch (`txManager.ts:91-164`) — it carries the identical `wait()===0` +
  `baseNonce+attempt` bug and all live callers already use the multi-chain
  `ctx` path (`txManager.ts:81-88`, which has no retry/nonce logic of its own and
  delegates wholly to the strategy). Per D-ROLLBACK (no legacy fallback paths) it
  is a re-introduction hazard. Verify no caller depends on the legacy overload
  before removing.

### Test fidelity, hash recording, and the pre-21-07 gate (captured under D-QUALITY-FIRST)
- **D-TEST-BOTH:** Cover the fixes at **both** unit level (mock the strategy's
  submit so `wait()`/relay reports failure while `getTransactionReceipt` /
  `getTransactionCount` say landed — replaying the LADYS scenario; analogs for
  bloXroute axios-timeout and passthrough wait-timeout) **and** fork level (the
  `eth-v3-trailing.json` full-lifecycle replay). D-04 observable-effect rigor:
  each test asserts a concrete observable (returned hash, DB `trades` row,
  unchanged nonce / no second submit, pino field).
- **D-RECORD-REAL-HASH:** Now that the strategy returns the real hash even on a
  reconciled-late inclusion, **persist it** on the buy trade row instead of the
  `txHash:'mev_bundle'` placeholder + `status:'pending'` (`bot.ts:728/735` V3,
  V2 analog) — improves auditability and is exactly the position-tracking the bug
  destroyed. Keep it tightly coupled to the fix; do not perturb unrelated
  capture-path behavior.
- **D-FORK-REHEARSAL-21.1:** Fork-rehearse the reconciliation/nonce-safe-retry
  logic before the 21-07 real-capital retry. A local fork has no Flashbots relay,
  so the false-negative path is unit-proven (mock) and validated for real on the
  21-07 retry; the fork rehearsal proves the surrounding buy→register→exit wiring
  still works end-to-end (mirrors Phase 21 D-FORK-REHEARSAL).

## Specific Ideas

- **The owner principle (D-QUALITY-FIRST) shaped every choice** — it flipped the
  retry policy from "fail cleanly / minimal surface" to capped fee-escalation,
  and widened the blast radius from Flashbots-only to all three strategies +
  legacy deletion.
- **The LADYS scenario is the canonical regression** — `wait()` (or a relay/
  wait timeout) reports failure while `getTransactionReceipt(hash)` /
  `getTransactionCount` prove the tx landed. The test must assert SUCCESS (hash
  returned, position registered) AND no second submit (no double-spend).
- **Reliable inclusion is a capital-safety property, not throughput** — the
  fee-escalation justification is the *sell/exit* leg (`executeFullSell`), where
  a non-included exit strands a position.
