### IN-01: HI-01 pre-broadcast re-check over-reserves public-buy gas (double-counts the buy-gas term) — strictly conservative, not a capital risk

**File:** `src/bot.ts:664-698` → `src/preflight.ts:408-435`

**Issue:** The HI-01 re-check reuses the full deliberate-mode floor, which reserves the public buy's
gas TWICE: once as `worstCaseBuyGas` (`maxGasLimit × maxFeePerGas`, preflight.ts:410) and again as the
deliberate `worstCasePublicBuyGas` term (preflight.ts:423-431). At the *re-check* point — where the
remaining work is exactly one public buy + the guaranteed public sell — only ONE public-buy-gas term is
strictly needed. The extra reservation makes the re-check stricter than necessary, so a marginal buy
sitting in the narrow band `[floor_single_reserve, floor_double_reserve)` would be refused even though
it is genuinely affordable.

**Why it is NOT a defect:** the over-reservation is in the FAIL-SAFE direction (it can only refuse, never
over-broadcast / strand the exit), and it is the IDENTICAL formula the step-0 gate already applied, so it
introduces NO new false refusal relative to a buy that already passed step-0 with unchanged
balance/fee (confirmed by the calm-gas happy-path test). Reusing the single-source gate verbatim was
also exactly what the finding required ("do NOT hand-roll a new reserve formula"), so this is a
deliberate, defensible trade of a slightly-tighter bound for single-source-of-truth simplicity.

**Optional fix (only if a tighter bound is ever wanted):** at the re-check, price the floor in `'snipe'`
mode with `buyValueWei = amountInWei` (which drops the extra `worstCasePublicBuyGas` term but keeps
`worstCaseBuyGas` + `worstCasePublicSellGas` + cushion). Not recommended for capital safety — the
current conservatism is the safer choice and matches the project's decision-quality preference.

### IN-02: WR-03 guard admits a legitimately-zero quote (`amountsOut[1] === 0n`) → public buy with `minOut = 0` (pre-existing slippage edge, not introduced by the fix)

**File:** `src/bot.ts:712-730`

**Issue:** The WR-03 guard rejects a malformed/short array and a `null` element but `0n == null` is
`false`, so a quote of `amountsOut[1] === 0n` passes the guard and flows to
`computePublicMinOut(0n, slippagePct)` → `minOut = 0n` (accept any output). A public buy with
`minOut = 0` is sandwichable. This only arises if the pool genuinely quotes zero out for the input —
a degenerate/near-empty pool state.

**Why it is Info, not a finding:** WR-03 only ADDED protection (the prior code would have crashed
uncaught on a short array); it did not introduce the zero-quote case, which is the same
`computePublicMinOut` behavior the codebase has had since 21.2-13 (the helper itself documents the
`minOut = 0` accept-any case). The practical exposure is small (a zero quote on a token the operator
deliberately chose to buy), and the operator-gated live path is the only way to reach it.

**Optional fix:** treat `amountsOut[1] === 0n` as a quote failure in the WR-03 guard
(`|| amountsOut[1] === 0n`) so a zero quote also fails closed with `op:'buy.fallback.quote-failed'`
rather than broadcasting an unprotected buy. Low priority; consider folding into the next deliberate-buy
touch rather than a standalone change.
