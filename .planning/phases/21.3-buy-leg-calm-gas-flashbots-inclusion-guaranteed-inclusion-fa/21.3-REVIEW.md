**The capital-safety core is largely sound.** I verified the high-priority focus items directly:

- **DOUBLE-SPEND (focus #1):** the no-double-buy guard reconciles the REAL broadcast hash (`BroadcastHandle.signedTxHash` via `escalatePrivateBuy` → strategy side-channel — not a pre-signed phantom), fails closed on `included`/`landed-not-ours`/`reverted`/inconclusive, and the chain-truth defense-in-depth requires `balanceOf==0 AND nonce-not-consumed`. The single-nonce authority (`withNonceLock`) holds. The REAL-PATH test (`noDoubleBuyReconcile.test.ts`) exercises the real `escalatePrivateBuy → sendTxWithRetry → passthrough strategy → submitWithReconciliation` chain and asserts hash equality on the broadcast hash. **No double-spend path found.**
- **FRONT-RUN (focus #2):** `swapExactETHForTokensSupportingFeeOnTransferTokens` is reachable ONLY from `executeDeliberateBuy` (bot.ts:640). The V2/V3 pair-event snipe sites use `swapExactETHForTokens` privately and `submitBuyTx` (private-only, fail-clean). **Snipes never reach the public mempool.**
- **CR-01 clamp (focus #3):** not regressed. The strategy uses `a.priorityFeeWei` directly (flashbots.ts:210) with no second `max()`; `chainPriorityWei` is folded in BEFORE the clamp in the helper (reconciliation.ts:511-514). The raised `MEV_BUY_MAX_PRIORITY_FEE_GWEI` is INPUT-only.
- **UNMONITORED position (focus #4):** all three landed deliberate branches (private-landed, late-land-included, public) route through `recordAndArmDeliberateBuy → armPositionMonitoring`. The V2 snipe extraction is byte-equivalent to the prior inline block (verified against `be0e6f5~1`). `deliberateBuyArmMonitoring.test.ts` covers all branches with the real path.
- **NONCE authority (focus #5):** the private leg, the no-double-buy guard, and the public fallback all run under `withNonceLock(ctx.wallet.address)`.
- **SECRET leakage (focus #6):** telemetry (`getBundleStatsV2`) logs only pubkeys/booleans; the fail-clean and fallback alerts carry only public values. `flashbotsMultiBuilder.test.ts` asserts no `AUTH_KEY`/signed-raw-tx in the stats log.

## Critical Issues

### CR-01: Deliberate-buy affordability gate validates the wrong amount (`chain.snipeAmount`, never the operator's `amountInWei`) — can strand a deliberate buy's own exit

**File:** `src/bot.ts:481-491` (caller) → `src/bot.ts:288-301` (`enforceEntryExitAffordability`) → `src/preflight.ts:370-424` (`checkEntryExitAffordability`)

**Issue:**
`executeDeliberateBuy(ctx, targetToken, amountInWei, dex)` receives the operator-supplied spend `amountInWei` (from `scripts/deliberate-buy.ts:82,142`, an arbitrary `parseEther(amountArg)`), but the affordability gate it calls **ignores it entirely**:

- `enforceEntryExitAffordability(ctx, targetToken, 'deliberate')` passes only `mode` — never the amount.
- `checkEntryExitAffordability(chain, mode)` computes the floor from `const snipeValue = ethers.parseEther(chain.snipeAmount)` (preflight.ts:397) — the static per-chain config, **not** the deliberate amount.

So the gate computes `floor = snipeValue(chain.snipeAmount) + buyGas + publicSellGas + publicBuyGas + cushion` and compares it to the balance, but the actual deliberate spend is `amountInWei`, which can be arbitrarily larger.

**Failure scenario (capital loss — unexitable position):**
`chain.snipeAmount = "0.01"`, wallet holds 0.05 ETH. Operator runs `deliberate-buy.ts eth <token> 0.04`. The gate validates against 0.01 ETH and PASSES. The private leg's strategy-level clamp (`computeAffordablePriorityFee` uses the real `txRequest.value = 0.04`) would catch unaffordability and throw, falling through to the public path — but **the public fallback path (`swapExactETHForTokensSupportingFeeOnTransferTokens`, bot.ts:617-649) has NO affordability re-check at all.** It spends 0.04 ETH directly. The wallet is left below the reserved guaranteed-public-exit gas → the position can become **unexitable** — the exact Finding A thin-wallet trap this gate exists to make impossible to enter. There is no double-spend (single-nonce holds), but the deliberate position can be entered with no guaranteed exit.

**Why the tests miss it:** every deliberate test uses `AMOUNT_IN = 0.01 ETH` and `snipeAmount: '0.01'` (noDoubleBuyReconcile.test.ts:125,153; deliberateBuyArmMonitoring.test.ts:170,195), so the two values coincide and the substitution is invisible. `exitAffordability.test.ts` only asserts the mode and the formula terms — never a deliberate amount diverging from `snipeAmount`.

**Fix:** thread the real buy value into the gate and use it as the `snipeValue` term. Minimal shape:
```ts
// preflight.ts
export async function checkEntryExitAffordability(
  chain: PreflightChain,
  mode: 'snipe' | 'deliberate' = 'snipe',
  buyValueWei?: bigint,   // NEW: actual buy value; defaults to parseEther(chain.snipeAmount)
): Promise<PreflightResult> {
  ...
  const snipeValue = buyValueWei ?? ethers.parseEther(chain.snipeAmount);
  ...
}

// bot.ts enforceEntryExitAffordability — add a buyValueWei param and pass it through:
async function enforceEntryExitAffordability(
  ctx, targetToken, mode = 'snipe', buyValueWei?: bigint,
): Promise<boolean> {
  const result = await checkEntryExitAffordability(
    { ...ctx.chain, httpProvider: ctx.httpProvider, wallet: ctx.wallet }, mode, buyValueWei,
  );
  ...
}

// executeDeliberateBuy (bot.ts:489):
if (!(await enforceEntryExitAffordability(ctx, targetToken, 'deliberate', amountInWei))) return null;
```
Snipe call sites (bot.ts:976, 1311) leave `buyValueWei` undefined → byte-for-byte unchanged. Add a regression test where the deliberate amount EXCEEDS `chain.snipeAmount` and the wallet covers the snipe floor but not the deliberate floor (must REFUSE).

## High

### HI-01: Public deliberate-buy fallback has no affordability/balance bound — direct router call can over-spend the exit reserve

**File:** `src/bot.ts:617-649`

**Issue:**
The public-mempool leg of the deliberate buy is a direct `router.swapExactETHForTokensSupportingFeeOnTransferTokens(..., { value: amountInWei })`. Unlike the private leg, it does **not** pass through `submitWithReconciliation` / `computeAffordablePriorityFee`, so nothing re-validates that, after this `amountInWei` spend, the wallet still holds the guaranteed-public-exit reserve. The ONLY upstream protection is the step-0 affordability gate — which (per CR-01) validated `chain.snipeAmount`, not `amountInWei`.

This is the second half of the same trap as CR-01 but is independently worth fixing: even if CR-01 is fixed, the public leg re-reads no live balance (the private leg may have escalated gas, the base fee may have risen since the gate), so a marginal deliberate buy at the boundary can still strand its exit. The guaranteed-public-EXIT (sell) ladder it mirrors (`executePublicFallbackSell`) is a sell of an already-held token (no new ETH out), so it never faced this; the buy spends fresh ETH and must.

**Failure scenario:** wallet at the deliberate floor; base fee rises between the gate and the public broadcast; the public buy spends `amountInWei` + the higher gas, leaving less than the reserved public-sell gas → unexitable position.

**Fix:** before the public broadcast (after the no-double-buy guard clears, bot.ts:617), re-run the affordability check against the live balance and `amountInWei` (reuse `computeAffordablePriorityFee` or a slim `balance - amountInWei - publicBuyGas - publicSellReserve >= cushion` check), and abort fail-closed on failure with a D-ALERTS log. This keeps the "never enter what you cannot exit" invariant on the only path that actually broadcasts a public buy.

## Warnings

### WR-01: Raw multi-builder fanout submits to block+1 BEFORE the reconcile hash is obtained — a mid-loop relay error re-introduces the LADYS false-negative

**File:** `src/utils/mevStrategies/flashbots.ts:261-291`

**Issue:**
In the submit closure, the raw `eth_sendBundle` fanout loop (lines 261-267) runs FIRST and actually submits the bundle to the relay/builders for block+1 (and possibly block+2..N). The library `sendBundle` call that yields the deterministic reconcile hash (`bundle.bundleTransactions[0].hash`) runs only AFTER the loop (line 274). If a later iteration's `rawSendBundle` returns `res.error` (line 264) or its `resp.assertOk()` throws (line 106) — e.g. a transient relay 5xx on the block+2 send — the closure throws WITHOUT ever reaching line 274, so `result.signedTxHash` is never produced and the `BroadcastHandle` is never written for this attempt. Meanwhile the bundle submitted to block+1 is live and can land. The reconciler then has no hash to probe for this attempt → a bundle that lands is treated as a failure: zero record, unmonitored position — the exact LADYS false-negative this phase exists to kill.

Severity is Warning (not Critical) because it requires a relay error AFTER at least one successful raw submit, and the deterministic-bytes design means the NEXT attempt's nonce-advance check could still catch it — but on a single-attempt budget (snipe ceiling-hit, or `DELIBERATE_BUY_PRIVATE_ATTEMPTS=1`) there is no next attempt.

**Fix:** derive the deterministic hash from `signedBundle` (or do the library `sendBundle` for block+1) and write the `BroadcastHandle`/`signedTxHash` BEFORE the raw fanout loop, so any mid-fanout throw still leaves a reconcilable hash. The signed bytes are already hoisted (line 230) precisely so they can be reused; compute the hash from them up front.

### WR-02: No-double-buy chain-truth check uses absolute `balanceOf==0`, not a pre-buy delta — a deliberate buy of an already-held token can never use the public fallback

**File:** `src/bot.ts:584-608`

**Issue:**
The chain-truth defense-in-depth aborts the public buy if `heldBalance !== 0n || nonceConsumed` (line 589). `heldBalance` is the absolute `balanceOf(targetToken)` (line 585), taken with no pre-buy baseline. If the wallet already holds ANY of `targetToken` before the deliberate buy (a prior partial position, an airdrop, dust), the guard always trips on `heldBalance !== 0n` and the public fallback is permanently blocked — even when `nonceConsumed === false` proves precisely that the private buy did NOT land. The OR makes the (correct, precise) nonce signal moot whenever a non-zero starting balance exists. This is fail-closed (capital-safe — no double-spend), but it silently and confusingly defeats a legitimate deliberate buy.

The sell guard's `balanceOf` check works because a sell consumes a known held balance; the buy's "balanceOf must be 0" wrongly assumes a zero starting balance.

**Fix:** snapshot `balanceOf` at the top of `executeDeliberateBuy` (before any submit) and compare the delta: `tokensReceived = heldBalanceNow - heldBalanceBefore; if (tokensReceived !== 0n || nonceConsumed) abort`. Then the balance signal means "did THIS buy's tokens arrive", consistent with the intent in the bot.ts:472 comment.

### WR-03: Public deliberate-buy quote (`getAmountsOut`) is unguarded — a short/empty array or RPC throw aborts uncaught after the guard cleared

**File:** `src/bot.ts:621-623` (and the same shape at 502-503)

**Issue:**
The public path does `const amountsOut = await router.getAmountsOut(amountInWei, path); const expectedOut = amountsOut[1];` with no try/catch and no length check. If `getAmountsOut` reverts (e.g. pair removed mid-flight) or returns a malformed/short array, `amountsOut[1]` is `undefined` and `computePublicMinOut(undefined, ...)` throws a bigint TypeError. This happens AFTER the no-double-buy guard cleared but BEFORE the broadcast, so it is not a double-spend (the script exits 2, no ETH out) — but it is an ungraceful crash on a recoverable condition, with no D-ALERTS. The private quote at 502-503 IS wrapped (defaults to `minOut=0`), so the inconsistency is also a smell.

**Fix:** wrap the public quote in try/catch (or guard `amountsOut.length < 2`), and on failure emit a structured `op:'buy.fallback.quote-failed'` log + alert and return null (fail-closed) rather than throwing uncaught.

## Info

### IN-01: `submitBuyTx`'s `_mode` parameter is dead — mode threading into it has no effect

**File:** `src/bot.ts:262-268` (and call sites 1005, 1332)

**Issue:** `submitBuyTx(ctx, txBuilder, _mode = 'snipe')` documents that it "does NOT branch on mode" and the parameter is `_`-prefixed/unused. The snipe sites pass `'snipe'` explicitly but it is discarded. The real mode-awareness lives only in `enforceEntryExitAffordability`. The vestigial parameter implies a behavioral switch that does not exist. **Fix:** drop the `_mode` parameter from `submitBuyTx` and its call sites, or add a comment that it exists purely for call-site symmetry. Low priority.

### IN-02: `publicBuyAllowed` flag + its `if (!publicBuyAllowed)` guard is dead code

**File:** `src/bot.ts:534, 609-615`

**Issue:** `publicBuyAllowed` is only ever set to `true` (line 609) and every abort path `return`s before reaching it, so `if (!publicBuyAllowed)` (line 611) is unreachable. The code comment acknowledges it as defensive. It is harmless but adds noise. **Fix:** acceptable to keep as an explicit fail-closed sentinel; otherwise remove. No action required for correctness.

### IN-03: Private deliberate quote falls back to `minOut = 0` on a quote failure

**File:** `src/bot.ts:499-506`

**Issue:** if the private quote (`getAmountsOut`) throws, `privMinOut` stays `0n`, so the private buy accepts any output. Because the private leg goes through Flashbots (not the public mempool), it cannot be sandwiched, so the practical front-run risk is nil — but `minOut=0` also disables slippage protection against a genuinely bad pool state at fill time. Acceptable given the private routing, but worth an explicit log assertion that this only applies to the private leg. The public leg correctly recomputes its own `minOut` (subject to WR-03). No capital-safety action required.
