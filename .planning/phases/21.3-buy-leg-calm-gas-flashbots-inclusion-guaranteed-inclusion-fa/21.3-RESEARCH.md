## Summary

The 2026-05-29 LADYS buy failure is **non-inclusion of a valid tx**, not a revert (proven by the `staticCall` returning ~242.38M LADYS even at 5% slippage). At a 0.25-gwei base fee a 13-gwei-priority single-tx bundle is wildly profitable, so the cause is almost certainly **builder coverage** — the validator that proposed the winning block used a builder (overwhelmingly beaverbuild.org or Titan, which together build ~88% of ETH blocks) that **never received the bundle**, because the bundle was submitted only to the Flashbots relay/BuilderNet and BuilderNet did not win those four slots. This is exactly the failure mode the locked decisions target, and it is **fixable privately** (no public-mempool exposure) via multi-builder fanout.

The single most important implementation fact this research surfaces: **the installed Flashbots library version (1.0.0, the latest) physically cannot send the `builders` field** — it drops it from the RPC params. The multi-builder fanout must be implemented as a **raw `eth_sendBundle` JSON-RPC call** that reuses the library's signed bundle (`signBundle`) and the same `X-Flashbots-Signature` auth header. Everything else in the phase reuses proven 21.1/21.2 machinery: the `submitWithReconciliation` loop, the leg-aware `buildReconcileConfig`, the affordability clamp, the `BroadcastHandle` no-double-spend reconcile, `withNonceLock`, and the public fee-on-transfer-safe router call (the buy analog of the proven `recover-sell-ladys.ts` sell).

**Primary recommendation:** Implement multi-builder fanout via a raw signed `eth_sendBundle` with a `builders` array (default the full 19-name registry, biased toward the dominant builders) + multi-block targeting (resubmit the same signed bundle to N consecutive target blocks per attempt, default `MEV_BUY_TARGET_BLOCKS=3`) + a raised but still-affordability-clamped buy ceiling (`MEV_BUY_MAX_PRIORITY_FEE_GWEI=25`, matching the proven sell-leg ceiling). Add `flashbots_getBundleStatsV2` telemetry (already available in the installed library) keyed on `consideredByBuildersAt` / `sealedByBuildersAt` to *prove* the root cause and confirm multi-builder inclusion live. **Do NOT add a coinbase bribe** (21.2 reached the identical conclusion and shipped `MEV_SELL_COINBASE_BRIBE_ENABLED=false`, wired nowhere). The deliberate-buy public path mirrors the proven `executePublicFallbackSell` ladder, inverted to a buy, gated behind explicit deliberate invocation, with the no-double-buy reconcile + mode-aware affordability reserve.

### Pattern 1: Raw `eth_sendBundle` with `builders` (the multi-builder mechanism)
**What:** Reuse the library to *sign* the bundle and to query stats, but build the `eth_sendBundle` RPC body yourself so you can add the `builders` array the library drops.
**When to use:** Every Flashbots buy submit (snipe and deliberate-private-leg).
**Example (reconstructed from the installed library's own request path):**
```typescript
// Source: VERIFIED against node_modules/@flashbots/ethers-provider-bundle/build/index.js:155-165,793-797
// The library's sendRawBundle drops `builders`; replicate its request + auth, add builders.
import { id, FetchRequest, Wallet } from 'ethers';

async function rawSendBundle(
  relayUrl: string,
  authSigner: Wallet,
  signedTxs: string[],            // from flashbotsProvider.signBundle([{signer, transaction}])
  targetBlock: number,
  builders: string[],             // MEV_BUILDERS — the registered builder names
): Promise<{ bundleHash?: string; error?: { message: string; code: number } }> {
  const params = {
    txs: signedTxs,
    blockNumber: `0x${targetBlock.toString(16)}`,
    builders,                     // ← the field the library omits (eth_sendBundle v2 param)
  };
  const body = JSON.stringify({ method: 'eth_sendBundle', params: [params], id: 1, jsonrpc: '2.0' });
  const req = new FetchRequest(relayUrl);
  req.setHeader('Content-Type', 'application/json');
  // SAME auth scheme the library uses (index.js:796): address:sign(id(body))
  req.setHeader('X-Flashbots-Signature', `${await authSigner.getAddress()}:${await authSigner.signMessage(id(body))}`);
  req.body = body;
  const resp = await req.send();
  resp.assertOk();
  return resp.bodyJson?.result ?? resp.bodyJson;   // {bundleHash, smart?: ...}
}
```
**Privacy note (CRITICAL for D-BUY-INCLUSION-PRIVATE-FIRST):** `eth_sendBundle` with `builders` is **still a private relay submission to registered builders** — it does NOT broadcast to the public mempool and does NOT expose the buy to front-running. Multi-builder fanout = more *private* builders see it, not public exposure. [VERIFIED: docs.flashbots.net/flashbots-auction/advanced/multiplexing — "All eth_sendBundle requests are shared with BuilderNet … multiplexed to other block builders"; this is builder-to-builder, not mempool]

### Pattern 2: Multi-block targeting per attempt
**What:** Send the *same* signed bundle to `block+1 … block+N` in one attempt, instead of only `block+1`.
**When to use:** Every buy attempt. Rationale: at calm gas a single target block frequently lands on a slot whose proposer used a builder that did not get the bundle; targeting N consecutive blocks raises the odds that at least one winning-builder slot covers the bundle. [CITED: docs.flashbots.net/flashbots-auction/advanced/troubleshooting — "Late receipt of the bundle, preventing its inclusion in the target block" + single-block targeting interacts with builder rotation]
**Example:**
```typescript
// In the submit closure, after signBundle + simulate(block+1):
const head = await provider.getBlockNumber();
const targets = Array.from({ length: targetBlocks }, (_, i) => head + 1 + i);
for (const tb of targets) {
  const res = await rawSendBundle(relayUrl, authSigner, signedTxs, tb, builders);
  if (res.error) throw new Error(`Flashbots error: ${res.error.message}`);
}
// Then bundle.wait() on the library bundle for block+1 as the native confirm signal,
// and reconcile the deterministic signed-tx hash across the window (unchanged).
```
**Interaction with the existing per-attempt window:** `submitWithReconciliation` already polls a `confirmWindowMs` (default 45s ≈ 3-4 blocks) per attempt, so the receipt probe already spans multiple blocks. Multi-block *submission* makes the bundle *eligible* in each of those blocks; the existing reconcile then catches inclusion in any of them. The two compose cleanly — no loop restructuring needed.

### Anti-Patterns to Avoid
- **Adding `builders` via `opts` on `flashbotsProvider.sendBundle(...)`:** silently dropped by the installed library — the bundle goes out with no builder list, so the "fix" would be a no-op that *looks* correct in code review. Verified by reading `index.js:155-163`. **This is the trap.**
- **Routing the snipe buy through any public path:** violates D-BUY-INCLUSION-PRIVATE-FIRST. Multi-builder fanout is the private fix.
- **Reserving the private *ceiling* in the affordability bound:** the 21.2 code already retargeted the reserve to the *guaranteed public exit* price (`computePublicExitReserveWei`, base-fee × buffer, no priority-fee term). Do NOT regress this — the buy ceiling raise must touch the ceiling INPUT only (`reconciliation.ts:294-319`).
- **Pre-signing a phantom tx for the no-double-buy reconcile:** the 21.2-12 CR-02 lesson — reconcile the `BroadcastHandle` hash the strategy ACTUALLY broadcast, never a locally re-built tx.

## Common Pitfalls

### Pitfall 1: The `builders` field silently dropped by the library
**What goes wrong:** Adding `builders` to `flashbotsProvider.sendBundle(..., opts)` compiles and runs but the bundle goes out with no builder list — the multi-builder fix is a no-op.
**Why it happens:** `@flashbots/ethers-provider-bundle@1.0.0` `FlashbotsOptions` only declares `minTimestamp/maxTimestamp/revertingTxHashes/replacementUuid`, and `sendRawBundle` hardcodes the params object (index.js:155-163), so any extra opt is discarded.
**How to avoid:** Use the raw `eth_sendBundle` path (Pattern 1). The unit test must assert the wire body contains a non-empty `builders` array (not just that `sendBundle` was called).
**Warning signs:** Bundle still not included at calm gas in live telemetry; `getBundleStatsV2.consideredByBuildersAt` only ever shows BuilderNet's pubkey.

### Pitfall 2: Multi-block resubmission re-signing with a fresh nonce
**What goes wrong:** Re-signing the bundle per target block re-fetches the nonce and can sign a *different* tx, breaking the deterministic-hash reconcile and risking a second tx if the nonce advanced.
**Why it happens:** Naively calling `signBundle` inside the per-block loop.
**How to avoid:** Sign ONCE per attempt (the helper already supplies the attempt nonce), then send the SAME `signedTxs` to all N blocks. The deterministic signed-tx hash is the reconcile key — it must be identical across all N submissions.
**Warning signs:** `reconcileInclusion` probes a hash with no receipt despite the nonce advancing.

### Pitfall 3: Confusing multi-builder fanout with public-mempool exposure
**What goes wrong:** A reviewer (or a future heuristic) treats `builders` as "going public," weakening the snipe-protection guarantee, or rejects the fix as MEV-unsafe.
**Why it happens:** Conflating "more builders" with "the mempool."
**How to avoid:** Document inline that `eth_sendBundle` + `builders` is builder-to-builder private routing (Pattern 1 privacy note). Registered builders do not leak the bundle to the public mempool. [VERIFIED: docs multiplexing]
**Warning signs:** A PR comment proposing to gate `builders` behind the deliberate flag — it should apply to ALL buys, including snipes.

### Pitfall 4: The double-BUY (uniquely unrecoverable)
**What goes wrong:** A late-landing private bundle + a public fallback both spend ETH → real ETH out twice for one position.
**Why it happens:** Public fallback fires before confirming the private bundle did not land.
**How to avoid:** The single per-wallet nonce makes two same-nonce txs structurally impossible (at most one lands); the `BroadcastHandle` reconcile before the public buy is the procedural guard — `included`/`landed-not-ours`/inconclusive ALL abort (fail-closed). Mirror the 21.2 guard at `exitEngine.ts:902-961` exactly, inverted to "ETH out is the danger." Add a defense-in-depth check: before the public buy, also confirm `balanceOf(token) == 0` (no tokens already received) AND the wallet ETH balance is consistent with no spend.
**Warning signs:** Two buy txs at adjacent nonces; token balance > expected single buy.

### Pitfall 5: Raising the ceiling without confirming the clamp still binds
**What goes wrong:** `MEV_BUY_MAX_PRIORITY_FEE_GWEI=25` is read but the affordability clamp is bypassed, letting a buy overspend ETH a thin wallet needs for the exit reserve.
**Why it happens:** Re-introducing a `max()` against the unclamped chain rate in the submit closure (the original CR-01 bug).
**How to avoid:** The buy ceiling raise is a `buildReconcileConfig` INPUT change only; the submit closure must keep using `a.priorityFeeWei` directly (flashbots.ts:129-130). At a 0.25-gwei base fee the affordability bound on a thin wallet may itself be the binding clamp — that is correct and intended.
**Warning signs:** `mev.escalation.unaffordable` never fires on a thin wallet, or the submitted priority fee exceeds the affordability bound.

### Q7 — No-double-BUY guard (highest stakes)
**Finding (HIGH):** The single per-wallet nonce via `withNonceLock` makes a double-SPEND structurally impossible: the private bundle and the public fallback both acquire the same per-wallet nonce chain, and the strategy re-fetches `getTransactionCount('latest')` per attempt and STOPS on advance — so at most ONE tx with a given nonce can land. [VERIFIED: nonceAuthority.ts:60-75 + reconciliation.ts:459-480]
**The procedural guard (mirror 21.2 exactly, inverted):** Before the deliberate public buy, run `reconcileInclusion(broadcast.signedTxHash, broadcast.submittedNonce, …)` on the REAL last-broadcast handle (NOT a pre-signed phantom — the 21.2-12 CR-02 lesson). Outcomes (map from exitEngine.ts:902-961):
- `included` → the private buy landed late → **ABORT the public buy**, treat as a landed buy (record the real hash).
- `landed-not-ours` / inconclusive → cannot prove the private buy did NOT land → **fail-closed, do NOT buy publicly** (a double-spent ETH buy is unrecoverable). Re-evaluate on a retry.
- `reverted`/`not-landed` → fall through to a defense-in-depth chain-is-truth check, then the public buy.
**Chain-is-truth (D-OP-DB-TRUTH) defense-in-depth for the buy:** Because ETH-OUT (not token-out) is the danger, before the public buy ALSO verify on-chain: (a) `balanceOf(token) == 0` (no tokens already received by a landed private buy) AND (b) the nonce was NOT consumed (`getTransactionCount('latest') == submittedNonce`). If tokens are present or the nonce advanced, ABORT. This is stricter than the sell's balance check because a buy's harm is spending ETH twice, not selling tokens twice. [VERIFIED pattern: exitEngine.ts:963-979 zero-held guard, inverted]
**Where the danger differs from the sell:** Sell double-action = sell tokens you have (recoverable: you got ETH twice for tokens you held). Buy double-action = spend ETH twice for one intent (UNrecoverable). So the buy guard's bias must be even harder toward "do not broadcast when in doubt." The BroadcastHandle is already populated by both Flashbots and passthrough strategies even on a throw (flashbots.ts:224-226, passthrough.ts:163-164) — reuse it directly.
