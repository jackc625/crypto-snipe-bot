# Phase 19 — UI Design Contract

> Visual and interaction contract for the dashboard surfaces introduced by Phase 19 (anti-rug runtime monitoring). Generated by `gsd-ui-researcher`. Verified by `gsd-ui-checker`.

This phase extends an established React 19 + Tailwind v4 + lightweight-charts dashboard that the operator runs locally to supervise live mainnet trading. It is NOT a public-facing UI. The design contract here is a delta on top of the existing token set in `dashboard/src/index.css` and the existing component vocabulary in `dashboard/src/components/`. Every new surface MUST reuse the existing tokens, components, and conventions — no new design language, no new icon library, no new font.

The phase delivers six new dashboard surfaces, all consumed by an operator who has to decide, often under time pressure, whether a rare-but-high-stakes anti-rug event represents a real loss being prevented, a false positive being suppressed, or a system fault being escalated. The UI must therefore favour: (a) calm at-a-glance status, (b) hard-to-miss alarms when something is actually wrong, and (c) deep evidence on demand for the audit trail. Anti-rug exits are rare; CB-tripped is "hard-to-miss"; WS-health gets pinged only for real outages.

## Interaction Contracts

### Anti-Rug column behaviour

- Column inserts BETWEEN `Exit Mode` and `Time Held` in `PositionTable.tsx` header / body — this places it adjacent to the exit-mode signal, which is the closest semantic neighbour (both describe "what will happen on exit").
- Cell click does NOT toggle the existing row expand/collapse — it opens the `AntiRugExitDetailModal`. Click event on the badge must `e.stopPropagation()` to prevent the row toggle (precedent: `PositionTable.tsx:194-196` Force Sell button).
- Badge state is push-updated via the WS `antirug_state_update` event; no per-row polling.

### CB-banner interaction

- Banner is sticky at the top of the Overview when any chain has a tripped CB; pushes the page header down.
- Multi-chain trips collapse into one banner with one chip per tripped chain inside the banner; clicking a chip routes the reset modal to that chain.
- Banner has no dismiss control — only a successful reset hides it.

### CB-reset modal flow

1. Operator clicks `Click to review and reset` link inside the banner.
2. Modal opens with N trigger sections (default N=3 from `<CHAIN>_ANTIRUG_CIRCUIT_BREAKER_TRIGGERS`).
3. Each section shows full evidence (token, pair, signals, outcome, timestamp); each has an unchecked `I have reviewed this trigger` checkbox.
4. `Reset Circuit Breaker` button stays `disabled cursor-not-allowed` until all N checkboxes are checked.
5. After all checkboxes are checked, the `Type RESET to confirm` input field appears (animated reveal acceptable; not required).
6. Input must match `RESET` exactly (case-sensitive, per `ConfirmDialog.tsx:36` precedent) for the button to enable.
7. On click, fires `POST /api/anti-rug/circuit-breaker/{chain}/reset`; success closes the modal and hides the banner; failure renders the error string inline above the buttons and leaves the modal open with state preserved.

### Detail modal flow

- Opens via badge click (positions table) OR via Last-10-events row click (Anti-Rug Monitor tile).
- Backdrop click closes (matches `ConfirmDialog.tsx:58`).
- ESC closes.
- No tab-trap requirement (the dashboard does not currently implement focus trapping; Phase 19 does not introduce it — accessibility is a separate cross-cutting concern for a future phase).
- Tx-hash row is click-to-copy; copy success shows a 2-second `Copied!` toast in `text-profit text-xs` to the right of the row (no toast framework — inline span with `setTimeout` reset).

### Frontrun-distribution filter chips

- Click toggles the chip via the existing `FilterChips.tsx` toggle pattern.
- Multi-select (matches `EventFeed.tsx:38-54` behaviour).
- Empty selection = show all.

### WS-health indicator placement

- One per enabled chain. Rendered (a) in the sidebar footer next to the global WS dot, stacked vertically and (b) in `ChainStatusCard.tsx` WebSocket row (already present — Phase 19 extends the existing `chain.wsConnected ? 'Connected' : 'Disconnected'` string to `🟢 Connected (last pong {time-ago})` / `🟡 Reconnecting (last seen {time-ago})` / `🔴 Disconnected ({duration})`).
- No popover; tooltip text is the entire interactive surface (matches `Sidebar.tsx:34` `title={collapsed ? item.label : undefined}` pattern).

## Realtime Push Contract

Phase 19 adds 5 new event types to the existing `useWebSocket.ts` `switch (msg.type)` dispatch. No new transport, no new auth, no new payload format — every event is a `WsEvent<T>` per `dashboard/src/types/api.ts:122-126`.

| Event type | Payload shape (TypeScript sketch) | UI side-effect |
|------------|-----------------------------------|----------------|
| `antirug_state_update` | `{ tradeId: number, chain: string, state: 'live' \| 'dry-run' \| 'would-have-sold' \| 'exit-fired' \| 'halted' \| 'unmonitored', lastEventTs?: number, lastSignals?: { lpRemovedPct, destination, allowlistHit, sellSimSlippagePct } }` | Update the Anti-Rug column cell for that `tradeId`; merge `lastSignals` into the detail-modal state for that position |

| `cb_tripped` | `{ chain: string, triggers: Array<{ token, pair, signals, outcome, timestamp }>, windowHours: number, triggerCount: number }` | Render `CircuitBreakerBanner` with chip for this chain; pre-populate `CircuitBreakerResetModal` triggers list |

All events also produce a corresponding `notification` event (existing type) that flows into the EventFeed via `severity` mapping: `cb_tripped → 'error'`, `antirug_event` with `outcome: 'live-exit' → 'error'`, `antirug_event` with `outcome: 'dry-run-would-have-sold' → 'warning'`, `antirug_event` with `kind: 'allowlist-suppression' → 'info'`, `cb_reset → 'success'`, `chain_ws_health_change` with `state: 'disconnected' → 'warning'`. ## Cross-Cutting Constraints

1. **Local-only operator UI.** No CSP-hardening, no PII redaction, no public-share concern. The operator owns the machine. This relaxes some constraints (we can show full token addresses, full tx hashes, full ETH amounts) and tightens others (the operator IS the only fault-detector for the bot — design for "operator must notice this immediately" not "operator might notice in a daily digest").

2. **High-stakes audit trail.** Every anti-rug exit MUST be reconstructable from the dashboard alone: detection timestamp, signals at evaluation time, confirm-after-N-blocks history, exit tx hash, sell amount, ETH received, gas multiplier used, ROI vs entry. The detail modal is the single point of truth — design it to be screenshot-friendly (no animations, no auto-dismiss).

3. **V2 and V3 visual parity.** The Anti-Rug column shows the same six badge states regardless of pool type. The detail modal shows different signal labels (V2: `Reserves below sell-threshold`; V3: `Sell-sim slippage`) but the same evidence layout. Operator MUST NOT have to remember "is this row V2 or V3" to interpret the badge.

4. **Telegram parity.** Every state visible on the dashboard has a matching Telegram alert per CONTEXT.md D-VIS-LIVE-EXIT, D-VIS-CB-TRIPPED, D-VIS-WS-HEALTH. Dashboard surfaces are the canonical visual; Telegram is the asynchronous notification. Wording on Telegram SHOULD match the dashboard (e.g. dashboard banner `ANTI-RUG HALTED ON ETH — 3 triggers in last hour` → Telegram first line `[ANTI-RUG HALTED] ETH — 3 triggers in last hour`).

5. **Dark-mode only.** The existing dashboard has no light-mode toggle. Phase 19 does not introduce one. All colour values above are dark-mode hexes; no `dark:` Tailwind variants are needed.

6. **No new fonts, no new icon libraries.** Use Inter + JetBrains Mono + lucide-react exclusively. New icons that may be useful: `ShieldOff` (for halted state), `Eye` (for review CTA), `RefreshCw` (for reset), `AlertOctagon` (for CB banner left-edge marker), `Activity` (for WS-health), `Copy` (for tx-hash copy button) — all already in `lucide-react@^0.510.0` per the existing `Sidebar.tsx` import precedent.

7. **No new state-management library.** State flows: WS hub → `WebSocketContext` consumer hook → component. Local UI state via `useState`. No Redux, no Zustand, no Jotai. Modal open/close state lives in the parent page component (e.g. `Overview.tsx`) per the existing `forceSellTarget` pattern.
