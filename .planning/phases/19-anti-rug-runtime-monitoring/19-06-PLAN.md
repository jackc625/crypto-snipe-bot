<threat_model>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `POST /api/anti-rug/circuit-breaker/:chain/reset` operator endpoint | authenticated operator request crosses into bot process to clear a tripped circuit breaker; misuse (e.g., reset before reviewing triggers) bypasses the operator-protection signal |
| `CircuitBreakerResetModal` UI gate (N-acknowledge + RESET-text) | client-side gate; operator skipping checkboxes / typing wrong text is the failure mode; backend STILL accepts the POST (the backend trusts the operator credential) |
| `useWebSocket.ts` switch dispatch on 5 new events | external (server-controlled) WS messages cross into dashboard state; malformed payloads could break the rendering of the affected component |
| `GapDetectedBanner` localStorage dismissal | client-side state; survives browser refresh; could mask a NEW gap event if key collisions occur |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-19-06-01 | Spoofing | unauthenticated POST /reset | mitigate | Express route inherits the existing `authMiddleware` from src/api/server.ts (auth check before reaching `apiRouter.use`). Test 6 explicitly verifies the auth middleware applies. |
| T-19-06-02 | Tampering | operator skips checkbox-acknowledge gate (e.g., by manipulating DOM in devtools) | accept | The UI gate is a UX safety, not a security boundary. Backend trusts the operator's authenticated credential per existing dashboard conventions. The audit-trail is the structured pino `cb-reset` log + the recent-triggers persisted record — the operator can be held to "you reset without reviewing" via log review. |
| T-19-06-03 | Repudiation | CB reset endpoint succeeds but no audit trail | mitigate | Plan 19-05 + this plan emit `log.info({chain, op: 'cb-reset'})` from the resetCircuitBreaker call inside the route handler; ALSO broadcasts `cb_reset` event for dashboard + EventFeed history. |
| T-19-06-04 | Denial of service | hostile WS message floods the dashboard with cb_tripped events for fake chains | mitigate | Dashboard renders the chain chip only if `chain in contexts`; unknown chains are silently dropped (defensive narrowing on the cb_tripped payload). |
| T-19-06-05 | Information disclosure | tx hash + token addresses shown in detail modal | accept | All on-chain public data per UI-SPEC §Cross-Cutting Constraints item 1. Local-only operator UI. |
| T-19-06-06 | Elevation of privilege | malformed payload on antirug_state_update breaks state setter | mitigate | useWebSocket switch case wraps the payload-merge in a try/catch; on parse failure logs to console and skips the update; never throws to break the broader dispatch. |
| T-19-06-07 | Tampering | localStorage key collision in GapDetectedBanner across chains | mitigate | Key format `antirug-gap-dismissed-${chain}-${fromBlock}` includes both chain and fromBlock; a new gap event with a different fromBlock re-shows the banner per UX design. |
| T-19-06-08 | Repudiation | CB reset request fails silently in network — operator thinks reset succeeded | mitigate | UI shows inline error rendering per UI-SPEC §CB-reset modal flow step 7 ("on failure renders the error string inline above the buttons and leaves the modal open with state preserved"). Test 25 explicitly drills the failure path. |
| T-19-06-09 | Tampering | wrong-text input in CB-reset (e.g., 'reset' lowercase) bypasses confirm | mitigate | `requireConfirmText` machinery from ConfirmDialog.tsx is case-sensitive per existing precedent at :36. Test 24 explicitly asserts lowercase / trailing-space variants do NOT enable the button. |
| T-19-06-10 | Information disclosure | tx hash leaked to system clipboard (click-to-copy) | accept | Operator-initiated action; UI-SPEC explicit pattern per `formatters.ts` precedents. |

**Residual risk:** None at `high`. The dashboard surfaces are display-and-operator-input — the security model is "authenticated operator on a local machine"; the gating mechanisms (N-acknowledge + RESET-text) are operator-protection UX, not access control. The high-stakes flows (CB reset, dry-run-to-live flip) are explicitly designed to be hard-to-misuse but not impossible-to-misuse, matching the dashboard's existing EmergencyConfirmDialog precedent.
