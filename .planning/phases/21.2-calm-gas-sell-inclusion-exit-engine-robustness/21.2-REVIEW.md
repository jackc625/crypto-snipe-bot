# Phase 21.2: Code Review Report

**Reviewed:** 2026-05-29T01:24:08Z
**Depth:** deep (cross-file call-chain tracing)
**Files Reviewed:** 12
**Status:** issues_found

## Summary

Phase 21.2 reworks the exit engine to fix four capital-safety findings (no-double-sell ladder, balance-truth teardown, per-wallet nonce authority, liveness). The balance-truth teardown (Finding D), the affordability-clamp authority (CR-01), the entry affordability gate (Finding A gate), the v6→v7 migration, the two-stage SIGINT, and the restart-resume scans are all implemented correctly and fail safe in the dangerous direction.

However, **two CRITICAL defects undermine the core of the rework**, both masked by tests that mock or stub the exact mechanism that breaks:

1. **Re-entrant `withNonceLock` deadlock (CR-01 below):** the serial ExitWorker takes the per-wallet nonce lock for the *whole* submit, then `executeFullSell` takes the *same* lock again for its approval/public-fallback steps. `withNonceLock` is a non-reentrant promise-chain mutex, so the inner acquire waits for the outer to settle and the outer waits for the inner — permanent deadlock. Every routine worker-driven exit (trailing-stop / stop-loss / urgency) hangs forever, the watchdog frees the loop but the orphaned `executeFullSell` never reaches its `finally`, so the per-token sell-lock is held permanently — which then blocks the *anti-rug* emergency exit for that token too. The two tests that touch this path either substitute a fake executor or mock `withNonceLock` to a non-serializing pass-through, so the deadlock is invisible in CI.

2. **No-double-sell guard step (2a) probes a tx that was never broadcast (CR-02 below):** `escalatePrivateSell` pre-signs a *throwaway* tx (no fee escalation, no chainId) to derive `lastSignedHash`/`lastNonce`, but the MEV strategy re-builds, re-signs and broadcasts a *different* tx with the clamped escalation fees. The guard's `reconcileInclusion(priv.lastSignedHash, …)` therefore probes a hash that never hit the chain — its receipt is always null and it can never return `'included'`, so step 2a never aborts the public fallback. The only surviving guard is the single `balanceOf` snapshot (2b), which is racy against a private bundle that lands after the snapshot but before/with the public fallback → real double-sell window.

Both are direct regressions of the invariants this phase was chartered to protect (Finding A no-double-sell, Finding C nonce authority).

A separate **WARNING (WR-01)** notes that the buy path and buy-time approval bypass `withNonceLock` entirely, leaving a cross-submit nonce-collision window between buys and concurrent sells/anti-rug — contradicting the stated D-NONCE-AUTHORITY-ALL invariant ("buys … must route through withNonceLock").

## Critical Issues

### CR-01: Re-entrant `withNonceLock` deadlocks every worker-driven routine exit and permanently strands the token's sell-lock

**File:** `src/exitEngine.ts:1254` (worker drain) + `src/exitEngine.ts:826`/`829` (nested approval lock); `src/utils/nonceAuthority.ts:52-72`

**Issue:**
The ExitWorker drain wraps the whole submit in the per-wallet nonce lock:
```ts
await withNonceLock(item.ctx.wallet.address, () =>
    this.watchdog(item, () => this.executor(item)),   // executor === executeFullSell
);
```
`executeFullSell` then takes the **same** lock again for its approval (and, on the public-fallback path, for the approval + swap):
```ts
await withNonceLock(ctx.wallet.address, () => ensureApproval(token, dex.routerAddress, balance, ctx.wallet.address));
```
`withNonceLock` is a non-reentrant promise-chain mutex (`nonceAuthority.ts`): the inner call reads `chains.get(key)` — the still-pending **outer** `run` promise — and schedules its op `.then(op)` to execute only after the outer settles. But the outer cannot settle until `executeFullSell` returns, which is awaiting the inner op. **Permanent deadlock**, on every routine exit that reaches the (unconditionally-wrapped) approval step — i.e. all of them.

Consequences (capital-safety):
- Routine exits (trailing-stop, stop-loss, urgency) never complete via the worker — positions are never sold on those triggers.
- The watchdog times out at `WATCHDOG_BUDGET_MS` and frees the drain loop, but the orphaned `executeFullSell` promise stays pending forever and **never reaches its `finally { releaseSellLock(...) }`** (`exitEngine.ts:1083`). The per-token sell-lock is held permanently.
- The direct anti-rug path (`anti-rug/exitTrigger.ts:238` → `executeFullSell` → `tryAcquireSellLock`) then returns `false` for that token, so **even the emergency anti-rug exit is permanently blocked** for any token that had a routine trigger fire first.

Why CI missed it: `test/unit/exitEngine/exitWorker.test.ts` substitutes a fake executor via `_setSellExecutorForTesting` (never runs real `executeFullSell`), and `test/unit/exitEngine/exitInclusionLadder.test.ts:140-145` mocks `withNonceLock` as a non-serializing pass-through (`return op()`), which removes the promise-chaining that causes the deadlock. `nonceAuthority.test.ts` has no nested/reentrant case.

**Fix:** Do not double-lock. Either (a) make the worker NOT wrap the submit in `withNonceLock` and rely on `executeFullSell`'s internal per-signing-site locks (the worker is already serial-by-construction), or (b) make `executeFullSell` take the lock once around all signing and remove the per-call wraps, or (c) make `withNonceLock` reentrant for the same wallet on the same async context. Option (a) is the smallest correct change:
```ts
// drain():
await this.watchdog(item, () => this.executor(item));   // executeFullSell already nonce-locks each signing site
```
Add a regression test that drives the **real** `executeFullSell` through the worker with the **real** `withNonceLock` and an approval that fires, asserting it resolves (does not hang).

### CR-02: No-double-sell guard reconciles a pre-signed hash that is never broadcast; public-fallback double-sell race remains open

**File:** `src/utils/txManager.ts:156-167` (`escalatePrivateSell` pre-sign) + `src/exitEngine.ts:871-887` (guard step 2a)

**Issue:**
`escalatePrivateSell` derives the no-double-sell handle by locally signing a tx it builds itself:
```ts
const nonce = await ctx.httpProvider.getTransactionCount(ctx.wallet.address, 'latest');
const populated = await ctx.wallet.populateTransaction({ ...tx, nonce });   // NO fee escalation, NO chainId, NO type:2
const signedRaw = await ctx.wallet.signTransaction(populated);
lastSignedHash = keccak256(signedRaw);
```
But the actual broadcast happens inside `sendTxWithRetry → strategy.sendTransaction → submitWithReconciliation`, which **re-fetches its own `'latest'` nonce and re-builds the tx with the clamped/escalated `maxFeePerGas`/`maxPriorityFeePerGas` + `chainId` + `type:2`** (`flashbots.ts:109-130`, `passthrough.ts:85-129`) before signing/broadcasting. The signed bytes — and therefore the keccak256 hash — differ. `priv.lastSignedHash` is **not** the hash of any tx that ever hit the chain.

In the engine guard (2a):
```ts
const recon = await reconcileInclusion(priv.lastSignedHash, priv.lastNonce, …);
if (recon.outcome === 'included') { /* abort public fallback */ }
```
`reconcileInclusion` probes `getTransactionReceipt(priv.lastSignedHash)` — always null (that hash was never sent) — so it can never return `'included'`. The nonce-corroboration path returns at best `'landed-not-ours'`, which the engine does **not** treat as a late-land. So step 2a is dead: it never aborts the public fallback. The sole remaining guard is the single `balanceOf` snapshot in step 2b (`exitEngine.ts:893`). If the private bundle is still pending past the confirm window and lands *after* the `balanceOf` read, the public fallback sells the full balance and the private bundle also lands → **double-sell** — the exact harm Finding A's "reconcile the last private attempt before the public fallback" was supposed to prevent. The code comment claims this is "the proven 21.1 probe," but it is probing a phantom hash.

Why CI missed it: the inclusion-ladder test mocks `reconcileInclusion`/strategy hashes and asserts on the mocked return values, not on hash equality between the pre-signed handle and the broadcast tx.

**Fix:** Have the private leg return the **real** broadcast signed-tx hash + the **actual** submitted nonce (the strategy already computes both — `flashbots.ts:177-181` `bundle.bundleTransactions[0].hash`/`.nonce`; `passthrough.ts:151` `tx.hash`/`a.nonce`). Surface them from `sendTxWithRetry`/the strategy result so `escalatePrivateSell` returns the *broadcast* `txHash`/`nonce`, and delete the throwaway local pre-sign. Then step 2a's `reconcileInclusion` probes the real hash over the full confirm window and can actually detect a late land before the fallback. Until fixed, treat `landed-not-ours` from 2a as "do not run the public fallback" (fail safe toward not-selling-twice) as an interim mitigation.

## Warnings

### WR-01: Buy path and buy-time approval bypass `withNonceLock` — cross-submit nonce-collision window

**File:** `src/bot.ts:484` and `src/bot.ts:816` (`sendTxWithRetry` buy submit) + `src/bot.ts:207` (`maybeApproveForChain` direct `approve`)

**Issue:** The phase invariant (D-NONCE-AUTHORITY-ALL) and the `nonceAuthority.ts` header explicitly list "21.2-08 (buy entry path)" as a consumer, and the charter states "every signing submit (buys, sells, anti-rug, public fallback, approvals, partial sells) must route through withNonceLock." But `bot.ts` does not import or call `withNonceLock` at all — the V2 and V3 buy submits and the pre-buy approval sign directly. A buy and a concurrent sell/anti-rug on the same wallet (different tokens) can both fetch `getTransactionCount('latest')` before either lands and sign against the same nonce. The strategy's per-attempt stop-on-advance only catches advancement on the *next* attempt, not the initial collision, so the cross-submit serialization the lock exists to provide is absent on the buy side.

**Fix:** Wrap both buy submits and the buy-time approval in `withNonceLock(ctx.wallet.address, …)`:
```ts
const realHash = await withNonceLock(ctx.wallet.address, () => sendTxWithRetry(/* … */));
```
and `await withNonceLock(ctx.wallet.address, () => maybeApproveForChain(ctx, tokenContract, …))`.

### WR-02: Anti-rug exit bypasses the ExitWorker, so it is never watchdog-bounded (residual liveness gap)

**File:** `src/anti-rug/exitTrigger.ts:238` (direct `executeFullSell`) vs `src/exitEngine.ts:1244-1260` (watchdog only wraps the worker)

**Issue:** Only the three routine triggers call `enqueueExit` (`exitEngine.ts:1559/1583/1601`). The anti-rug exit calls `executeFullSell` directly, so it never passes through `this.watchdog(...)`. The most time-critical exit (an active rug) can therefore still hang for minutes on a stalled `bundle.wait()`/RPC with no wall-clock bound, parking the event loop — the very symptom (T-21.2-HANGSUBMIT) Finding B set out to bound. The watchdog header claims it bounds "EACH submit"; it bounds only worker submits.

**Fix:** Either route anti-rug through the worker (enqueue with rank 0) or wrap the direct `executeFullSell` call (or its internal submit) in the same wall-clock race used by `makeExitWatchdog`/`withTimeout`.

### WR-03: Priority-queue anti-rug pre-emption is never exercised in production (comment-vs-code mismatch)

**File:** `src/exitEngine.ts:696-704` (`reasonRank`) + worker header `exitEngine.ts:666-668`

**Issue:** The worker header and `reasonRank` document that "a late-arriving anti-rug (0) jumps ahead of an already-queued trailing stop (2)." But anti-rug never enqueues (WR-02) — it calls `executeFullSell` directly — so rank 0 is dead in production. The priority ordering only ever ranks `urgency`/`stop-loss`/`trailing` against each other. The behavior the comment promises (anti-rug pre-emption) does not occur.

**Fix:** Either enqueue anti-rug (making the ranking real, and incidentally giving it the watchdog from WR-02) or correct the comment to state that anti-rug runs on the direct path and is not subject to queue ordering.

### WR-04: `escalatePrivateSell(attempts=0)` is silently promoted to 3 retries by `|| 3`

**File:** `src/utils/txManager.ts:191` → `src/utils/txManager.ts:94` (`const retries = (… ) || 3`)

**Issue:** `privateAttemptBudget` can return `0` if an operator sets `MEV_SELL_FALLBACK_ATTEMPTS=0` (`parsePositiveIntEnv` accepts `n >= 0`), and the txManager docstring even claims "anti-rug → 0-1". When `escalatePrivateSell` forwards `attempts=0` to `sendTxWithRetry`, the `(typeof walletOrRetries === 'number' ? walletOrRetries : maxRetries) || 3` expression treats `0` as falsy and substitutes `3`. An operator (or anti-rug path) asking for "no/one quick private attempt before the public fallback" silently gets up to 4 private attempts, delaying the guaranteed public exit and burning gas.

**Fix:** Replace `|| 3` with an explicit nullish/`<` guard, e.g. `const retries = typeof walletOrRetries === 'number' ? walletOrRetries : (maxRetries ?? 3);` and clamp negatives, so `0` is honored.

### WR-05: Reason-aware private-attempt budget is off-by-one vs its documented intent

**File:** `src/exitEngine.ts:52-55` (`privateAttemptBudget`) + `src/utils/mevStrategies/reconciliation.ts:441` (`for attempt = 0; attempt <= cfg.maxRetries`)

**Issue:** `privateAttemptBudget` returns `1` for anti-rug (doc: "ONE quick private attempt") and the default `2` for routine (doc: "2 attempts"). That value becomes `maxRetries`, and the strategy loop runs `attempt = 0 .. maxRetries` inclusive → `maxRetries + 1` submissions. So anti-rug actually makes **2** private attempts and routine makes **3** before the public fallback — one more than documented each. For anti-rug this delays the guaranteed exit while liquidity drains (the exact thing the "1 quick attempt" budget was meant to avoid).

**Fix:** Pass `attempts - 1` as `maxRetries`, or change the loop bound to `attempt < cfg.maxRetries`, and reconcile the docstrings. Add a test asserting the submission count equals the documented budget.

### WR-06: Partial sell still runs inline on the poll tick and can block it for the full confirm window

**File:** `src/exitEngine.ts:1517` (inline `await executePartialSell` in `pollExitStrategy`) + `src/exitEngine.ts:1388` (its `withNonceLock(… sendTxWithRetry)`)

**Issue:** Finding C decoupled the three full-sell triggers to the serial worker, but `executePartialSell` is still `await`ed inline on the poll tick. It calls `sendTxWithRetry → submitWithReconciliation`, which polls a bounded confirm window (default 45s) per attempt. A partial-sell trigger therefore blocks that position's poll cycle (and, because it holds `withNonceLock`, serializes against every other wallet submit) for tens of seconds — reintroducing the `overruns:true` poll-loop starvation Finding C was chartered to remove, for the partial-sell case. The worker header even asserts "partial-sell stays on the poll tick — it is non-blocking," which is not true given the reconciliation window.

**Fix:** Route partial sells through the same serial worker (or a dedicated non-blocking submit) and return `'continue'` immediately, mirroring the full-sell triggers; or document the residual blocking and confirm `pollTelemetry`'s `overruns` stays false under a real partial-sell submit.

## Info

### IN-01: `MEV_SELL_COINBASE_BRIBE_ENABLED` is a registered-but-unimplemented knob

**File:** `src/config.ts` (`MEV_SELL_COINBASE_BRIBE_ENABLED` spec)

**Issue:** The knob is registered with a behavioral description ("Encode a coinbase bribe in the exit bundle") but is read nowhere in `src/`. An operator setting it gets no effect, with no warning. Either implement it or mark the description clearly as reserved/not-yet-wired.

### IN-02: `fallbackSlippagePct` calls `parsePositiveNumberEnv(undefined, …)` — convoluted no-op parse

**File:** `src/exitEngine.ts:64`

**Issue:** `const routine = parsePositiveNumberEnv(undefined, CONFIG.slippagePercent || 5);` always returns the fallback because `raw` is `undefined`. This is just `CONFIG.slippagePercent || 5` written opaquely; it reads as if it parses an env var when it does not. Simplify to the direct expression for clarity.

### IN-03: `computePublicMinOut` yields `minOut = 0` (no slippage protection) for misconfigured slippage > 100%

**File:** `src/exitEngine.ts:77-82`

**Issue:** `keepPct = BigInt(Math.max(0, Math.round(100 - slippagePct)))` clamps to `0` when `slippagePct > 100`, making `minOut = 0` (accept any output, including a fully-sandwiched near-zero). The anti-rug floor (`Math.max(antiRug, 10, routine)`) and `parsePositiveNumberEnv` make this hard to hit operationally, but a defensive upper clamp (e.g. cap effective slippage at, say, 99%) would prevent an unbounded-loss public sell on a typo.

### IN-04: Fee-on-transfer dust remainder can flag a fully-sold position as "still held" and burn routine retries

**File:** `src/exitEngine.ts:200-207` (`computeDustThreshold`, default 1 bps) + `src/exitEngine.ts:990-1001` (success-path dust check)

**Issue:** With the default `EXIT_DUST_THRESHOLD_BPS=1` (0.01% of original), a fee-on-transfer token that leaves a >0.01%-of-original remainder after a genuine full sell is classified "still held," so the success path calls `keepMonitoringFailedHeld` and the position keeps re-triggering routine sells until the N=5 pause. This direction is fail-safe for capital (it errs toward keeping anti-rug), but it burns gas on already-effectively-closed positions and emits repeated "still held" alerts. Consider a larger default dust BPS, or treating "a sell landed and balance shrank toward dust over consecutive attempts" as a close.
