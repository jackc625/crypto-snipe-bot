### Locked Decisions

**D-QUALITY-FIRST [USER-BINDING] — governs everything:** at every choice pick the BETTER/SAFER/HIGHER-QUALITY option regardless of code complexity or LOC. "Minimal surface / least code / simplest" is NOT a virtue and must never be a tiebreaker.

**Finding A — Calm-gas exit inclusion**
- **D-EXIT-INCLUSION (layered ladder):** (1) escalate the sell privately with an INDEPENDENT, higher sell-leg priority-fee ceiling (decoupled from the buy ceiling), optionally + coinbase bribe; (2) fall back to a direct public-mempool sell — promote `scripts/recover-sell-ladys.ts` (`swapExactTokensForETHSupportingFeeOnTransferTokens`, fee-on-transfer-safe) into the engine. MEV protection when it works, guaranteed exit when it doesn't.
- **D-FALLBACK-TRIGGER (reason-aware):** anti-rug exits go public FAST (0–1 quick private attempts); routine exits (trailing/stop-loss/30-min urgency) escalate private for N attempts then fall back. A rug-in-progress must not retry private bundles while liquidity drains.
- **D-EXIT-AFFORDABILITY-GATE (hard entry gate):** at buy time, refuse the snipe unless the wallet can afford the WORST-CASE GUARANTEED exit (public-mempool sell gas + buffer). Strengthen `reserveSellGas` so its target is the guaranteed exit, not the private ceiling. Never enter a position you cannot exit.
- **D-FALLBACK-NO-DOUBLE-SELL:** before the public sell submits — (1) re-run 21.1's inclusion reconciliation (receipt + nonce) on the last private attempt and ABORT if it actually landed; (2) re-fetch on-chain balance and sell only what is still held. Reuses D-RECONCILE-RECEIPT + D-NONCE-SAFE-RETRY.

**Finding D — Failed-exit position protection**
- **D-FAILED-EXIT-KEEP-MONITORING:** anti-rug monitoring stays registered until genuine close (confirmed sell / on-chain balance ~0) NO MATTER how many exits fail. Routine retries are bounded: after N consecutive failures, pause ROUTINE retries + hard-alert; anti-rug emergency exits still fire. Corrects a misapplication of Phase 19 D-TERMINATION (NOT a reversal).
- **D-BALANCE-IS-TRUTH:** after any exit attempt, on-chain `balanceOf` is the source of truth: ~0 (dust threshold) → closed, tear down; > dust → still held, keep monitoring. Phase 21 D-OP-DB-TRUTH applied to the exit lifecycle.
- **D-PERSIST-FAILED-HELD:** on a failed exit of a still-held position, do NOT delete `exit_state`; mark a distinct status (e.g. `exit_failed_held`) separate from `sold`/`failed`(=dead) + a persisted failure counter; restart re-enters monitoring + re-registers anti-rug. Builds on D-23/EXIT-LIVE-02.

**Finding C — Poll-loop decoupling + bot-wide nonce safety**
- **D-DECOUPLE-SERIAL-WORKER:** poll ticks must never block on a sell — a tick that detects a trigger ENQUEUES and returns immediately; a single serial exit worker drains the queue one sell at a time; a per-position lock prevents re-entrant self-sell.
- **D-NONCE-AUTHORITY-ALL:** route EVERY signing tx (buys, exit sells, anti-rug sells, public fallback, approvals) through ONE per-wallet serialization / nonce authority. Eliminates the nonce-collision class bot-wide. Natural conclusion of 21.1's D-SHARED-HELPER.
- **D-EXIT-PRIORITY:** the serial worker processes queued exits by urgency: anti-rug > 30-min urgency / stop-loss > trailing-stop > partial-sell.

**Finding B — Freeze / kill-safety (defense-in-depth; root cause is a debug task)**
- **D-DEFENSE-IN-DEPTH:** add all three layers — (1) watchdog force-abort on wall-clock budget overrun + alert; (2) hard two-stage SIGINT; (3) timeouts on every provider/RPC call.
- **D-SIGINT-TWO-STAGE:** first SIGINT begins graceful shutdown (stop intervals, abort in-flight submit within a bounded grace period, flush state); second SIGINT OR grace-timeout → force `process.exit()`. Abandoning in-flight is safe because D-PERSIST-FAILED-HELD + D-NONCE-AUTHORITY-ALL make it recoverable.
- **D-WATCHDOG-ABORT:** on budget overrun the watchdog aborts JUST the stuck operation (AbortController / timeout rejection), logs + Telegram-alerts, keeps the bot alive monitoring everything else. The stuck position stays held + monitored per D-FAILED-EXIT-KEEP-MONITORING.

## Summary

The four findings collapse to **two root mechanisms** plus two policy gaps:

1. **The Flashbots `bundle.wait()` is a 5-minute, block-event-driven blocking call** that explains BOTH Finding B (freeze) and Finding C (~222s poll-loop block). The installed `@flashbots/ethers-provider-bundle@1.0.0` resolves `bundle.wait()` via `waitForBundleInclusion(..., TIMEOUT_MS)` where `TIMEOUT_MS = 5 * 60 * 1000`. That method registers `genericProvider.on('block', handler)` and only otherwise resolves on a 5-minute `setTimeout` that **`reject('Timed out')` with a bare string, not an Error**. Across 4 escalation attempts run synchronously inside `pollExitStrategy` → `submitWithReconciliation`, the await chain blocks the single Node event loop for ~3.7 minutes (the observed 222,605 ms), and the SIGINT handler — which competes for the same parked loop — appears unresponsive. The fix is structural (Finding C decoupling: enqueue + serial worker off the poll tick) AND defensive (Finding B: a wall-clock watchdog with `Promise.race`-style timeouts, because ethers v6 has no reliable per-RPC-call abort — confirmed by issues #4122/#4765 — and two-stage SIGINT).

2. **The affordability clamp caps the sell at the buy ceiling.** The sell leg reuses the SAME `MEV_MAX_PRIORITY_FEE_GWEI` (default 5 gwei) ceiling as the buy. On a thin wallet at calm base fee the affordability bound + this shared ceiling produced ~12.5 gwei, which a tiny no-MEV-value private bundle couldn't get included. The fix (Finding A) is an INDEPENDENT, higher sell-leg ceiling, then — when still not included — a guaranteed public-mempool sell (the proven `recover-sell-ladys.ts` path), guarded against double-sell by reusing 21.1's receipt+nonce reconciliation, and gated at buy time so the bot never enters a position it cannot guarantee an exit from.

3. **Finding D is a one-site logic bug with a test that encodes the bug.** `exitEngine.ts:561-573` (the `catch`) treats a FAILED exit the same as a successful close: `updateTradeStatus('failed')` + `clearAllTimersForToken` + `deleteExitState` + `unsubscribeAntiRug` — stripping rug protection from a still-held position. `test/unit/exitEngine/antiRugReason.test.ts` Test 6 asserts the error path DOES call `unsubscribeAntiRug` "per D-TERMINATION" — that test must be rewritten, not just the source. The fix: on a failed exit, re-fetch `balanceOf`; if > dust, KEEP monitoring + persist `exit_failed_held` + a failure counter; only tear down when balance ~0.

**Primary recommendation:** Build a single per-wallet `NonceAuthority` + serial `ExitWorker` (Finding C / D-NONCE-AUTHORITY-ALL) as the spine, layer the independent sell-leg ceiling + public fallback onto `submitWithReconciliation`/the worker (Finding A), rewrite the `executeFullSell` catch to be balance-truth-gated (Finding D), and wrap the whole thing in a watchdog + two-stage SIGINT + RPC-timeout helper (Finding B). No new npm dependencies are required — every mechanism reuses ethers v6, the existing Flashbots provider, better-sqlite3, and the 21.1 reconciliation helper.

### Pattern 1: Per-wallet NonceAuthority (serialization mutex over the EXISTING re-fetch scheme)
**What:** A single async-mutex keyed by wallet address. Every signing path acquires the lock, runs its submit (which itself re-fetches `getTransactionCount('latest')` per 21.1's D-NONCE-SAFE-RETRY), then releases. Serial-by-construction = nonce-safe for one wallet.
**When to use:** Wrap every call site that signs: buy submit (`bot.ts`), exit sell + public fallback + approvals (`exitEngine.ts`), anti-rug sell (routes through `executeFullSell` already), token approvals (`ensureApproval`).
**Why not ethers `NonceManager`:** it predicts/caches nonces optimistically; D-NONCE-SAFE-RETRY deliberately re-fetches `'latest'` and stops on advance. The mutex composes WITH that scheme; `NonceManager` would fight it.
**Home:** new `src/utils/nonceAuthority.ts`, exported as a singleton keyed by `wallet.address.toLowerCase()`. Extends the D-SHARED-HELPER centralization onto the txManager seam.

```typescript
// Source: pattern derived from reconciliation.ts:371 (re-fetch 'latest' per attempt) +
// exitManager.ts:14-25 (synchronous check-and-set mutex idiom, single-threaded JS).
// src/utils/nonceAuthority.ts  [ASSUMED signature — confirm with planner]
const chains = new Map<string, Promise<unknown>>(); // key: wallet address (lc)

/** Serialize a signing operation per wallet. The op itself re-fetches the
 *  'latest' nonce (D-NONCE-SAFE-RETRY); this only guarantees no two ops run
 *  concurrently for the same wallet, so no two ever contend for a nonce. */
export async function withNonceLock<T>(walletAddress: string, op: () => Promise<T>): Promise<T> {
  const key = walletAddress.toLowerCase();
  const prior = chains.get(key) ?? Promise.resolve();
  // chain the new op after the prior one (success OR failure — never block the queue)
  const run = prior.catch(() => {}).then(op);
  chains.set(key, run.catch(() => {})); // store a never-rejecting tail so the chain survives errors
  return run;
}
```

### Pattern 2: Serial ExitWorker draining a priority queue (D-DECOUPLE-SERIAL-WORKER + D-EXIT-PRIORITY)
**What:** A module-level singleton holding a priority queue and a `running` flag. `enqueueExit({tradeId, reason, ...})` inserts by priority and kicks the drain loop if idle. The drain loop dequeues one, `await`s `executeFullSell`, then continues — strictly one sell at a time.
**Priority order (reason → rank):** `anti-rug`(0) > `urgency-market-sell`(1) = `stop-loss`(1) > `trailing-stop`(2) > partial-sell(3). A late-arriving anti-rug jumps ahead of a queued trailing stop.
**Per-position lock:** before enqueue, check a `Set<chain:token>` of in-flight/queued positions; skip if present (no re-entrant self-sell). Extend `exitManager.ts`'s existing sell-lock map rather than inventing a parallel structure.

### Pattern 3: Finding A inclusion ladder inside executeFullSell (reason-aware)
**What:** Replace the single `sendTxWithRetry` (private only) with: private-escalation attempts (count by reason) → no-double-sell guard → public-mempool sell. The private leg uses an INDEPENDENT sell ceiling (`MEV_SELL_MAX_PRIORITY_FEE_GWEI`); the public leg uses `swapExactTokensForETHSupportingFeeOnTransferTokens` with reason-aware slippage.
**Reason → attempt count:** `anti-rug` → 0–1 quick private attempts (rug is now); routine (`trailing-stop`/`stop-loss`/`urgency-market-sell`) → N private attempts then fall back.

### Pattern 4: Balance-is-truth failed-exit catch (D-FAILED-EXIT-KEEP-MONITORING + D-BALANCE-IS-TRUTH)
**What:** rewrite `exitEngine.ts:561-573`. On ANY exit attempt completion (success or thrown), re-fetch `balanceOf`. If `<= dust` → genuine close (existing teardown). If `> dust` → still held: persist `exit_failed_held` + increment failure counter, KEEP timers + anti-rug registered. After N consecutive ROUTINE failures, pause routine retries + hard-alert; anti-rug emergency exits still fire.

### Anti-Patterns to Avoid
- **Calling `bundle.wait()` synchronously on the poll-cycle critical path** — it blocks up to 5 minutes (TIMEOUT_MS). This IS Finding B/C. The serial worker isolates it off the poll tick, and the watchdog bounds it.
- **`reject('Timed out')` with a bare string** (the Flashbots lib's own behavior) — when catching, never assume `err instanceof Error`; the codebase already guards with `e instanceof Error ? e.message : String(e)` (exitEngine.ts:572). Preserve that.
- **Deleting `exit_state` on a failed exit** (the Finding D bug). Never tear down state before `balanceOf` confirms ~0.
- **Re-using `MEV_MAX_PRIORITY_FEE_GWEI` for the sell ceiling** — that shared clamp is the Finding A trap. The sell ceiling must be an INDEPENDENT knob.
- **Bidding above the affordability bound to force inclusion** — the bound exists to guarantee the exit can still pay gas. Raising the sell ceiling must STILL respect affordability (the public fallback is the guaranteed path, not an over-bid private one).
- **Using ethers `NonceManager`** — conflicts with D-NONCE-SAFE-RETRY's re-fetch discipline.
- **`process.on('SIGINT')` returning into a parked event loop** — if the loop is blocked the handler never runs. The two-stage SIGINT's force-exit must be armed via a `setTimeout(...).unref()` that fires independently AND a second-signal listener (Node delivers a second SIGINT even mid-handler).

## Common Pitfalls

### Pitfall 1: The Flashbots `bundle.wait()` 5-minute block-event dependency (THE FREEZE)
**What goes wrong:** `bundle.wait()` → `waitForBundleInclusion(..., 300_000ms)` registers `genericProvider.on('block', handler)` and otherwise only resolves on a 5-min `setTimeout`. On an HTTP `JsonRpcProvider`, block events come from internal polling (`pollingInterval`); if polling is slow/stalled or the RPC hangs, the handler's `await getTransactionCount/getBlock` (no timeout) hangs, and the awaiting poll cycle blocks for up to 5 min PER attempt.
**Why it happens:** the await chain `pollExitStrategy → executeFullSell → sendTxWithRetry → submitWithReconciliation → submit() → bundle.wait()` runs synchronously on the single event loop; 4 attempts × the relay/block-bounded wait ≈ the observed 222,605 ms.
**How to avoid:** (a) decouple — the serial worker runs this OFF the poll tick (Finding C); (b) bound it — the watchdog aborts a submit exceeding the wall-clock budget; (c) wrap every provider call in `withTimeout`.
**Warning signs:** `exit.poll.cycle` `overruns:true` with `durationMs` in the hundreds-of-thousands; no logs for minutes; SIGINT unresponsive.

### Pitfall 2: SIGINT delivered into a parked loop never runs
**What goes wrong:** the current `gracefulShutdown` is a normal listener; if the loop is blocked in a synchronous await chain, the listener is queued but never executed — Ctrl+C "does nothing" (the observed symptom).
**How to avoid:** two-stage SIGINT where the force-exit is armed on an `unref()`'d timer AND a second-SIGINT listener. Critically, Finding C's decoupling is what actually keeps the loop free enough for the FIRST stage to run; the watchdog + force-exit are the safety net.
**Warning signs:** `taskkill /F /T` required to stop the process.

### Pitfall 3: Rewriting the source but leaving the test that encodes the bug
**What goes wrong:** `test/unit/exitEngine/antiRugReason.test.ts` Test 6 asserts the FAILED-exit path DOES call `unsubscribeAntiRug` "per D-TERMINATION". If you fix `exitEngine.ts` but not the test, the suite goes red — or worse, someone "fixes" the source back to match the test.
**How to avoid:** the plan must explicitly rewrite Test 6 to assert the OPPOSITE (failed-exit-still-held KEEPS the subscription) and keep Test 4/5 (genuine close DOES unsubscribe). Note this prominently in the plan's task list.
**Warning signs:** a green suite that still strips protection.

### Pitfall 4: Double-sell when the private bundle lands late
**What goes wrong:** the private bundle "not-landed" verdict can be wrong (the exact 21.1/STOP-THE-LINE-02 false-negative class) — it lands a block later, then the public fallback sells again → double-spend / sells nothing.
**How to avoid:** D-FALLBACK-NO-DOUBLE-SELL — before the public sell, run `reconcileInclusion` on the last private attempt (receipt + nonce); if included, ABORT. Then re-fetch `balanceOf` and sell only what's still held (so a partial late-land sells only the remainder).
**Warning signs:** two sell rows for one position; `landed-not-ours`; a public sell of a zero balance.

### Pitfall 5: Raising the sell ceiling past affordability strands the exit anyway
**What goes wrong:** a higher `MEV_SELL_MAX_PRIORITY_FEE_GWEI` that ignores the affordability bound could bid more than the wallet can pay, reverting the sell or leaving nothing for the public fallback gas.
**How to avoid:** the independent sell ceiling is still clamped by `computeAffordablePriorityFee`'s affordability bound. The GUARANTEED exit is the public fallback (cheaper, normal-priced), which the entry gate (D-EXIT-AFFORDABILITY-GATE) reserved for. The private ceiling is "try harder," not "exceed the budget."
**Warning signs:** `mev.escalation.unaffordable` on the sell; public fallback with insufficient gas.

### Pitfall 6: Watchdog abort that can't actually free the event loop
**What goes wrong:** an `AbortController` passed to a hung ethers call does nothing (ethers v6 doesn't honor it reliably — [#4122](https://github.com/ethers-io/ethers.js/issues/4122)). The watchdog "fires" but the loop stays parked.
**How to avoid:** the watchdog must rely on `Promise.race([op, rejectAfter(budget)])` to free the AWAITING code path (the abort signal is best-effort for the underlying socket; the freed promise is what matters). Combined with the serial worker decoupling, only ONE position's submit can ever be in-flight, so a freed worker can move on.
**Warning signs:** watchdog log fires but `overruns` continue.

// Source: pattern necessitated by ethers v6 limitation (#4122/#4765 — no reliable
// FetchRequest abort). src/utils/withTimeout.ts  [ASSUMED signature]
export async function withTimeout<T>(
  op: () => Promise<T>,
  ms: number,
  label: string
): Promise<T> {
  let timer: ReturnType<typeof setTimeout>;
  const timeout = new Promise<never>((_, reject) => {
    timer = setTimeout(() => reject(new Error(`RPC timeout after ${ms}ms: ${label}`)), ms);
    if (timer.unref) timer.unref();
  });
  try {
    return await Promise.race([op(), timeout]);
  } finally {
    clearTimeout(timer!);
  }
}
// Wrap provider calls: withTimeout(() => provider.getBalance(addr), RPC_TIMEOUT_MS, 'getBalance')

## Finding B Root-Cause Analysis (the deepest item — RESOLVED)

**Question:** Why did the event loop wedge on a MEV ceiling-hit, and why was SIGINT unresponsive?

**Root cause (HIGH confidence — verified against installed library source):**

1. **`bundle.wait()` is a long, block-event-driven blocking await.** In `@flashbots/ethers-provider-bundle@1.0.0`, `bundle.wait()` calls `waitForBundleInclusion(txs, targetBlock, TIMEOUT_MS)` with `TIMEOUT_MS = 5 * 60 * 1000`. That method:
   - registers `this.genericProvider.on('block', handler)` — it depends on the ethers provider emitting `'block'` events (HTTP `JsonRpcProvider` derives these from internal polling, governed by `pollingInterval`);
   - inside the handler, `await getTransactionCount(account)` and `await getBlock(targetBlock)` run with **no timeout**;
   - if no block event fires (polling stalled) or the RPC hangs, the ONLY resolution is the 5-minute `setTimeout`, which calls `reject('Timed out')` — **a bare string, not an Error**.

2. **It runs synchronously on the single event loop, inside the poll cycle.** The chain `setInterval → pollExitStrategy → executeFullSell → sendTxWithRetry → submitWithReconciliation → submit() → bundle.wait()` means each escalation attempt's `bundle.wait()` blocks the cycle. The 21.1 helper does up to `maxRetries+1` attempts; each `reconcileInclusion` ALSO polls a 45s confirm-window. Four attempts + their waits ≈ the observed **222,605 ms** `exit.poll.cycle overruns:true`.

3. **SIGINT appears dead because the loop is parked.** Node queues the SIGINT callback, but a synchronous-looking await chain that is genuinely awaiting a long network/timer resolution starves other microtasks/timers from making visible progress, and the existing `gracefulShutdown`'s own `setTimeout(...,5000)` force-exit competes with the same parked loop — so "Ctrl+C does nothing" until `taskkill`.

**Is there an unhandled rejection?** Possibly contributory: `reject('Timed out')` rejecting with a string can produce confusing logs (the `instanceof Error` guard matters), and any rejection not awaited becomes an unhandled rejection. But the PRIMARY mechanism is the synchronous-on-critical-path long wait, not a parked rejection.

**Why the defense-in-depth holds regardless:** even if a future library version changes these internals, the three layers (decoupled serial worker OFF the poll tick + wall-clock watchdog via `Promise.race` + two-stage SIGINT + per-RPC `withTimeout`) bound ANY long/hung operation. This is exactly why CONTEXT mandates all three rather than only a root-cause patch.

**STOP-THE-LINE check:** This root cause is WITHIN the scope of Findings B/C (it explains both). It is NOT a new bug class — no escalation needed. (See §Candidate STOP-THE-LINE Escalations for the items that ARE worth surfacing.)

## Open Questions (resolved Claude's-Discretion items)

### Q1 — Finding A inclusion ladder: independent ceiling, coinbase bribe, env defaults
- **What we know:** the sell currently reuses the 5-gwei buy ceiling (the trap). The Flashbots provider supports `sendBundle` with no per-bundle bribe arg; a coinbase bribe must be encoded as an extra tx in the bundle (`block.coinbase.transfer(...)`) or via a higher effective priority fee.
- **Resolution:** Ship the **independent sell-leg ceiling** (`MEV_SELL_MAX_PRIORITY_FEE_GWEI`, default ~25 gwei, still affordability-clamped) as the PRIMARY private lever. Make the **coinbase bribe env-gated and default-OFF** (`MEV_SELL_COINBASE_BRIBE_*`). Rationale (D-QUALITY-FIRST + cost/benefit): for a tiny no-MEV-value exit bundle, a bribe's marginal inclusion improvement is modest and it burns scarce capital on a thin wallet; the GUARANTEED inclusion lever is the public fallback, not an expensive bribe. The bribe is the next escalation if the 21-07 retry shows the independent ceiling alone is insufficient. **Attempt counts:** anti-rug → 0–1 quick private attempts; routine → 2 private attempts then public.

### Q2 — Entry affordability gate (D-EXIT-AFFORDABILITY-GATE)
- **Resolution:** at the snipe path (`bot.ts`, before submit), refuse unless `walletBalance >= snipeValue + worstCaseBuyGas + worstCasePublicSellGas + buffer`, where `worstCasePublicSellGas = maxGasLimit × (baseFee × SELL_GAS_BASEFEE_BUFFER) + approval gas` (the public sell is a normal-priced tx — no high priority fee, which is the whole point). Strengthen `computeAffordablePriorityFee`'s `reservedSellGas` to target the GUARANTEED public exit (currently it reserves the private CEILING priority fee, which over-reserves AND mis-targets). Align the buy-time gate's posture with `preflight.ts checkWalletBalance` (same `parseEther` + per-chain `gasBuffer` math). Buffer default per A8.

### Q3 — No-double-sell guard + slippage (D-FALLBACK-NO-DOUBLE-SELL)
- **Resolution:** before the public fallback submits: (1) `reconcileInclusion(lastAttemptSignedHash, lastNonce, ...)` — if `included`, abort the fallback (the private bundle landed late); (2) re-`balanceOf` and use that as `amountIn` (sell only what's still held; abort if 0). **Reason-aware slippage:** routine fallbacks reuse the engine's configured exit slippage (`CONFIG.slippagePercent`, ~5%); anti-rug fallbacks WIDEN (e.g. the proven 10% floor from `recover-sell-ladys.ts`, or wider) to maximize landing while liquidity drains.

### Q4 — Decoupling + nonce authority home/signature (D-DECOUPLE-SERIAL-WORKER + D-NONCE-AUTHORITY-ALL)
- **Resolution:** `NonceAuthority` lives in new `src/utils/nonceAuthority.ts` as `withNonceLock(walletAddress, op)` (a per-wallet promise-chain mutex). It composes WITH 21.1's re-fetch-latest scheme (does NOT replace it). The `ExitWorker` lives in `exitEngine.ts` (module singleton: priority queue + `running` flag + drain loop). The poll tick calls `enqueueExit(...)` and returns `'continue'`. Per-position lock extends `exitManager.ts`'s sell-lock map. Every signing site (`bot.ts` buy, `executeFullSell`, `executePartialSell`, `ensureApproval`, the public fallback) wraps its submit in `withNonceLock(ctx.wallet.address, ...)`.

### Q5 — Failed-exit protection (D-FAILED-EXIT-KEEP-MONITORING + D-BALANCE-IS-TRUTH + D-PERSIST-FAILED-HELD)
- **Resolution:** rewrite `executeFullSell` so that on BOTH the success path AND the catch, the teardown decision is made by a re-fetched `balanceOf`: `<= dust` → genuine close (existing teardown); `> dust` → still held: `upsert exit_state` with status `exit_failed_held` + `exit_failure_count++`, KEEP timers + anti-rug. After `exit_failure_count >= N` (default 5) consecutive ROUTINE failures, pause routine retries + hard-alert; anti-rug emergency exits still fire (they bypass the routine-pause). Dust threshold per A6 (relative to `original_token_amount`). On restart, `resumeExitMonitor` re-enters `exit_failed_held` rows into monitoring + re-registers anti-rug. **Plus: rewrite `antiRugReason.test.ts` Test 6** (Pitfall 3).

### Q6 — Finding B budgets/grace/timeouts
- **Resolution:** watchdog budget ~60s (must exceed one 45s confirm-window + margin; A3); SIGINT grace ~8s (A4); per-RPC timeout ~15s (A5). All env-tunable. ## Security Domain

> `security_enforcement` default (no `false` override found) = enabled. This is a funded-mainnet capital-safety phase; the relevant threats are financial/operational, not classic web auth.

### Applicable ASVS Categories
| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no | No user auth surface in this phase (signing key is `PRIVATE_KEY`, unchanged) |
| V3 Session Management | no | — |
| V4 Access Control | partial | SIGINT/shutdown is operator-only; no new network surface |
| V5 Input Validation | yes | All new env vars parsed via the existing `parsePositiveInt/Number/BoolDefaultTrue` helpers (reconciliation.ts:564-585) — never `NaN`, never negative; bigint math only for fees/amounts (no float drift) |
| V6 Cryptography | yes | NEVER hand-roll signing/nonce crypto — reuse ethers `Wallet`; the nonce authority is a serialization mutex, NOT a custom nonce predictor |

### Known Threat Patterns for this stack
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Double-spend / nonce collision (two txs same nonce) | Tampering | D-NONCE-AUTHORITY-ALL serialization + 21.1 re-fetch-'latest'-and-stop-on-advance |
| Double-sell (private lands late + public fallback) | Tampering / financial | D-FALLBACK-NO-DOUBLE-SELL: reconcile receipt+nonce before fallback; sell only held balance |
| Stranded position (can't exit) | Denial of capital | D-EXIT-AFFORDABILITY-GATE entry gate + public-mempool guaranteed exit |
| Unprotected held position (rug after failed exit) | Loss of funds | D-FAILED-EXIT-KEEP-MONITORING + D-BALANCE-IS-TRUTH (Finding D) |
| Frozen process holding a position (can't intervene) | Denial of service / operational | D-DEFENSE-IN-DEPTH watchdog + two-stage SIGINT + RPC timeouts (Finding B) |
| Secret leakage in logs | Information disclosure | Existing discipline (flashbots.ts:196 logs only public bundleHash/minedTxHash, never the signed raw tx or `FLASHBOTS_AUTH_KEY`) — preserve in all new log lines |
| Sandwich on the public fallback | Tampering / MEV | Accepted tradeoff per D-EXIT-INCLUSION (a sandwiched sell beats a stranded position); reason-aware slippage limits the worst case |
