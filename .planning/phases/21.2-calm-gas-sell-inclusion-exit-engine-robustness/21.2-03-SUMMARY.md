# Phase 21.2 Plan 03: Calm-Gas Sell Inclusion + Exit-Engine Robustness (DB v6→v7 exit_failed_held persistence) Summary

**DB schema v6→v7 additive ALTER-guard migration that persists a still-held FAILED exit on the `exit_state` table — a distinct `exit_status='exit_failed_held'` marker plus a persisted, restart-monotonic `exit_failure_count` — so a failed exit of a still-held position is no longer deleted, survives restart, is operator-visible, and feeds the bounded-routine-retry logic the 21.2-07 write path and the 21.2-10 fork restart-resume test depend on.**

## Decisions Made
- **Status + counter on `exit_state`, not a `trades.status` CHECK rewrite (RESEARCH A9).** SQLite cannot ALTER a CHECK constraint, so the trades path is the heavy recreate-table-with-copy pattern (db.ts:83-107) that drops and rebuilds the trades table — risk to the only production row. The additive ALTER on `exit_state` (the lifecycle table already keyed by trade_id) is both lighter AND safer. Chosen for safety per D-QUALITY-FIRST, not because it is fewer lines.
- **Two columns added as a pair under one guard.** The PRAGMA guard checks `exit_failure_count`; if present, BOTH ALTERs are skipped. Because they are only ever added together inside one transaction, a partial-rerun after a mid-transaction crash re-adds both or neither — never a half-migrated v7.
- **Counter persists across restart and is monotonic.** `exit_failure_count = exit_failure_count + 1` reads the stored value inside the UPDATE, so a reboot does not reset it — which is the whole point of persisting it (the bounded-retry logic in 21.2-07 counts consecutive failures across restarts). A genuine close calls `deleteExitState` (removing the row + counter); a fresh re-buy starts a new row at the DEFAULT 0.
- **Production-singleton version assert must be a floor.** See Deviations — the v7 bump broke the pauseState test's hard-pinned `=== 6`; the higher-quality fix is the floor-assert pattern lpBaseline already established.
