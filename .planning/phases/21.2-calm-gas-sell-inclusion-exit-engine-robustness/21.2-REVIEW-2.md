## High

### NF-01 (HIGH): CR-02 fail-safe early-return strands an anti-rug position — no re-armed poll timer, no `exit_failed_held` persistence

**File:** `src/exitEngine.ts:943-945` (the `privateInclusionInconclusive` early return) interacting with `src/anti-rug/exitTrigger.ts:240` (`clearAllTimersForToken` before the sell) and `src/exitEngine.ts:687-732` (`keepMonitoringFailedHeld`, the only re-arm + persist site)

**Issue:**
The CR-02 fix added an interim fail-safe: when guard 2a reconciles the private
leg as `landed-not-ours` (nonce consumed, our receipt not visible), it sets
`privateInclusionInconclusive = true` and returns early:
```ts
if (privateInclusionInconclusive) {
    return false;          // exitEngine.ts:944 — skips BOTH 2b AND the success/catch teardown
}
```
The comment justifies this with "the position is kept held + monitored
(balanceOf truth on the next cycle re-decides)." That is true for a **routine**
trigger (trailing-stop / stop-loss / urgency), whose 5s poll interval was never
cleared (routine triggers return `'continue'`). It is **NOT** true for an
**anti-rug** trigger:

1. `triggerAntiRugExit` calls `clearAllTimersForToken(chain, token)` BEFORE the
   sell (`exitTrigger.ts:240`), which deletes the `exitMonitorInterval`
   (`exitManager.ts:210-211`).
2. The private leg returns `landed-not-ours` → `executeFullSell` returns at
   `exitEngine.ts:944`, **bypassing `keepMonitoringFailedHeld`** — the ONLY code
   path that (a) re-arms the poll timer via `hasExitMonitorTimer` + `resumeExitMonitor`
   (`exitEngine.ts:723-732`) and (b) stamps `exit_status='exit_failed_held'`
   via `markExitFailedHeld` (`exitEngine.ts:700`).
3. Result: the position is left with anti-rug STILL registered (good) but with
   **NO routine poll timer** and **NOT persisted as `exit_failed_held`**.

This directly violates the documented invariant in `detector.ts:1370-1373`:
"executeFullSell's balance-truth catch keeps anti-rug registered **+ re-arms the
poll timer** while balanceOf > dust." On this branch it does neither.

Two harms compound:
- **No routine retry.** The "next poll cycle" the comment relies on does not
  exist for anti-rug — the timer was cleared. The position only ever re-exits if
  a NEW anti-rug WS signal happens to fire again; after the LP is already pulled
  there may be no further `safe→unsafe` transition to re-trigger on, so the
  position can sit un-retried.
- **Dropped on restart (regression of S-1 / T-21.2-DROPRUG).** Because
  `markExitFailedHeld` never runs, `exit_state.exit_status` stays NULL. The buy
  row for a settled position is `status='sold'`, so the restart-resume scan
  (`db.ts:597-604`, `getResumeExitMonitorTrades`: `WHERE status='pending' OR
  exit_status='exit_failed_held'`) will NOT pick it up. The very class of harm
  gap plan 21.2-11 closed is silently reintroduced for this one branch.

**Why CI missed it (same masking pattern the first review flagged):**
`test/unit/exitEngine/noDoubleSellReconcile.test.ts:359-389` exercises the
inconclusive branch with reason `'trailing-stop'` (a routine exit whose timer is
never cleared) and mocks `hasExitMonitorTimer` to `true` (`:88`). It asserts the
public swap did NOT fire and `result===false`, but never asserts the re-arm or
the `exit_failed_held` persistence, and never drives the **anti-rug** reason on
the inconclusive branch. The cleared-timer path is invisible.

**Fix:** On the inconclusive branch, take the keep-monitoring path instead of a
bare `return false`, so the timer is re-armed and the position is persisted as
`exit_failed_held` (still NOT running the public fallback — the no-double-sell
posture is preserved). Re-fetch the balance for the truth check, then:
```ts
if (privateInclusionInconclusive) {
    // Do NOT public-fallback (no-double-sell), but DO keep the position
    // monitored exactly like a failed-still-held exit so the timer is re-armed
    // (anti-rug cleared it) and the row is persisted for restart-resume.
    const held: bigint = await token.balanceOf(ctx.wallet.address).catch(() => -1n);
    const dust = computeDustThreshold(readOriginalTokenAmount(tradeId));
    if (held >= 0n && held <= dust) {
        teardownGenuineClose(ctx, tokenAddress, tradeId);   // it actually closed
        return true;
    }
    await keepMonitoringFailedHeld(ctx, dex, tokenAddress, feeTier, reason, tradeId, held);
    return false;
}
```
Add a regression test that drives the **anti-rug** reason through the inconclusive
branch with `hasExitMonitorTimer` returning `false` and asserts `markExitFailedHeld`
ran AND `resumeExitMonitor` re-armed the timer.

## Medium

### NF-02 (MEDIUM): Same-tick partial dispatch can silently no-op a full-sell trigger via the sell-lock, then mask the still-armed retry

**File:** `src/exitEngine.ts:1683-1686` (`dispatchPartialSell`) + `src/exitEngine.ts:1716/1740/1758` (full-sell `enqueueExit`) + `src/exitEngine.ts:801-804` (`executeFullSell` sell-lock acquire)

**Issue:**
WR-06 made the partial sell fire-and-forget on the poll tick, then the SAME tick
falls through to the trailing/stop-loss/urgency checks. If a tick both dispatches
a partial AND enqueues a full sell (e.g. price gapped through a partial tier and
the trailing stop on the same tick), the detached `executePartialSell` holds the
per-token sell lock (`tryAcquireSellLock`, `exitEngine.ts:1431`). When the worker
drains the enqueued full sell, `executeFullSell` calls `tryAcquireSellLock`
(`:801`), fails, logs "Another exit already handling token, skipping", and returns
`false` — the full sell is silently dropped for that tick.

This is recoverable (the routine trigger re-fires next poll cycle, and the
per-position queue lock is released after the no-op drain so re-enqueue works),
so it is not a capital-loss bug. But it is a behavioral surprise the WR-06 comment
("the per-token sell lock prevents a duplicate partial … a same-tick full sell
that enqueues simply fail[s] to acquire and no-op[s]") acknowledges only in
passing: a trailing-stop/stop-loss that the operator believes fired actually
no-opped behind an in-flight partial of up to one confirm window (default 45s).
On a fast dump, deferring the full exit by one or more poll cycles while a partial
holds the lock can matter.

**Fix:** Either (a) when a full-sell trigger fires on the same tick, prefer it
over the partial (skip `dispatchPartialSell` and enqueue the full sell — a full
exit supersedes a partial), or (b) have the worker's `executeFullSell` no-op be
explicitly observable (distinct op + an enqueue-retry) rather than relying on the
next poll cycle, and document the bounded deferral. Option (a) is the safer
capital posture (a full exit should win over a partial).

## Low

### NF-03 (LOW): `dispatchPartialSell` persists tier completions only on the detached promise; a crash between submit and `.then` loses the tier-completed state

**File:** `src/exitEngine.ts:1574-1590` (`dispatchPartialSell` persists `state.completedTierIndices` inside the `.then`)

**Issue:**
Pre-WR-06, the partial sell was awaited inline and the poll tick's step-8
`upsertExitState` persisted the mutated `completedTierIndices` on the same tick.
Now the persist happens only inside the detached promise's `.then` (`:1589`),
AFTER the confirm window. The poll tick that dispatched it already returned (it
does NOT persist the in-flight partial's tiers). If the process is killed (SIGKILL,
crash, OOM) between a successful on-chain partial sell and the `.then` running
`upsertExitState`, the tier is marked completed in-memory but never persisted —
on restart the position re-evaluates the same tier as unfilled and may sell it
again (a duplicate partial of an already-sold tier). The window is small (one
confirm cycle) and the loss is bounded (one extra partial, clamped to held
balance), so this is LOW, but it is a new durability gap the inline-await path did
not have.

**Fix:** Persist `completedTierIndices` immediately after the on-chain partial
confirms inside `executePartialSell` (right after `state.completedTierIndices.add`
at `:1516-1518`), so the persist is co-located with the state mutation rather than
deferred to the detached `.then`. The next-poll-tick step-8 persist remains a
backstop.
