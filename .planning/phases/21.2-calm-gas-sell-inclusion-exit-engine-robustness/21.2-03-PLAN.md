<objective>
Land the DB schema v6→v7 migration that persists a still-held failed exit (D-PERSIST-FAILED-HELD,
Finding D). On a failed exit of a still-held position the engine must NOT delete `exit_state`; it
marks a distinct status `exit_failed_held` (separate from `sold` and from `failed`=dead) and bumps
a persisted failure counter that drives the bounded-routine-retry logic. On restart, `exit_failed_held`
rows re-enter monitoring + re-register anti-rug.

Per RESEARCH A9 + Runtime State Inventory, the new status + counter live on the `exit_state` table
(the monitoring-lifecycle table, already keyed by trade_id) — this is the ADDITIVE ALTER-guard path
(`db.ts:185-189` idiom), explicitly chosen OVER recreating the `trades.status` CHECK constraint
(SQLite can't ALTER a CHECK; that path is heavier and risks the trades table). This plan ships ONLY
the schema + statements; the exit-engine logic that writes them lands in 21.2-07.

Purpose: persist the stuck-held state so it survives restart and is operator-visible.
