<objective>
Ship the Finding B defense-in-depth liveness layers (D-DEFENSE-IN-DEPTH): a wall-clock WATCHDOG +
a two-stage hard SIGINT (the RPC-timeout helper `withTimeout` already shipped in 21.2-02). Root cause
(verified): the Flashbots `bundle.wait()` is a 5-minute, block-event-driven blocking await run
synchronously on the poll critical path; 4 attempts ≈ the observed 222,605 ms freeze, and SIGINT
delivered into a parked loop never runs. Finding C's serial-worker decoupling (21.2-05) already moved
the long wait OFF the poll tick; this plan adds the safety net so ANY long/hung op is bounded and the
process is ALWAYS killable.

CRITICAL (RESEARCH Candidate-Escalation #3): the two-stage SIGINT must REPLACE the existing
single-stage `gracefulShutdown` (`bot.ts:1396-1445`), NOT augment it — the existing 5s force-exit timer
competes with the parked loop (the Finding B symptom itself). Do not leave two competing force-exit
timers.

Layers:
- **Watchdog (D-WATCHDOG-ABORT):** wall-clock budget (`WATCHDOG_BUDGET_MS` ~60s, must exceed one 45s
  confirm-window + margin) per submit/cycle; on overrun it aborts JUST the stuck op via `Promise.race`
  (NOT a relied-upon AbortSignal — ethers v6 doesn't honor it reliably), logs + Telegram-alerts, and
  KEEPS the bot alive monitoring everything else. The stuck position stays held + monitored per
  21.2-07 (D-FAILED-EXIT-KEEP-MONITORING) and is retried.
- **Two-stage SIGINT (D-SIGINT-TWO-STAGE):** first SIGINT/SIGTERM → graceful (stop intervals, flush —
  exit_state is already persisted each cycle, abort in-flight best-effort) + arm a force-exit
  `setTimeout(...).unref()` over `SIGINT_GRACE_MS` (~8s); a SECOND signal OR the grace-timeout →
  `process.exit()` immediately. Abandoning an in-flight submit is SAFE because 21.2-07
  (D-PERSIST-FAILED-HELD restart-resume) + 21.2-01 (D-NONCE-AUTHORITY-ALL) make it recoverable.

21.2-02 and the worker from 21.2-05.
