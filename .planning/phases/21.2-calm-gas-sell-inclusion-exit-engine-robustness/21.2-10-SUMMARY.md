**The design contract (promised, never implemented):**
- RESEARCH.md:469 — "On restart, `resumeExitMonitor` re-enters `exit_failed_held` rows into monitoring + re-registers anti-rug."
- 21.2-07-SUMMARY.md:166 — "a reboot must re-enter `exit_failed_held` rows into monitoring + re-register anti-rug."
- db.ts:529 comment — "On restart, getExitState surfaces exit_status so the row re-enters monitoring + re-registers anti-rug."

**The source reality (confirmed by grep + the new Test 3 D.1 assertion):**
- `exit_status` is ONLY ever WRITTEN (db.ts:542 `markExitFailedHeld`). It is **never READ anywhere in `src/`** — no resume scan, no preflight consumes it.
- The balance-truth CATCH stamps a still-held failed exit `trades.status='failed'` (exitEngine.ts:1054).
- Both bot reboot scans filter `trades.status='pending'` ONLY:
  - `resumeMultiChainMonitoring` — bot.ts:1275 `WHERE status='pending' AND action='buy'`
  - `resumeAntiRugMonitoring` — bot.ts:1391 `WHERE t.status='pending' AND t.action='buy'`
- ⇒ a catch-path `exit_failed_held` row is **SILENTLY DROPPED on reboot**: NOT re-monitored, anti-rug NOT re-registered.

**Why this is exactly the LADYS-class harm (capital-safety):** Finding D / T-21.2-DROPRUG exists to guarantee a still-held position that failed its exit NEVER loses rug protection. The in-process keep-monitoring (21.2-07) is correct, but it does NOT survive the reboot this plan was meant to prove. The held LADYS (~252.9M, tradeId 1) is precisely a still-held position whose monitoring was lost when the process died — re-arming it across a restart is the entire point of `exit_failed_held` persistence, and that re-arm is not wired. This FALSIFIES the premise that 21.2-07 fully delivered STOP-THE-LINE-04-D's restart-resume.

**Why it was NOT fixed in flight (D-STOP-THE-LINE + plan scope):**
- The fix is a `src/` change (add `OR e.exit_status='exit_failed_held'` to BOTH reboot scans AND join exit_state, and/or stop flipping `trades.status` to a scan-excluded value) — outside this plan's `files_modified` (`test/fork/*` only).
- It touches startup-resume control flow + the trades-status lifecycle → an architectural change (deviation Rule 4 / new decimal STOP-THE-LINE), NOT a fix-in-flight.
- Per the user-binding "don't auto-defer confirmed findings" rule, this is RE-SURFACED to the operator (here + the executor return), not file-and-deferred.

**Recommended disposition:** a new STOP-THE-LINE / decimal phase (e.g. 21.2-STOP-THE-LINE-05 or 21.3) that wires the reboot scans to re-enter `exit_failed_held` rows + re-register anti-rug, with a unit test on the corrected scan predicate and Test 3's D.1 expectations flipped to `true`.
