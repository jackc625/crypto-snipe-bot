Per D-03, D-04 and AC-48. Addresses review HIGH on 23-01 (a transaction count that advances on acceptance makes an unmined submission look mined, while production stops retrying on `latest`, `src/utils/mevStrategies/reconciliation.ts:478`). Plan 23-01 built the mined-only count and relay acceptance on the bundle path; this task completes that same state for every route. Node state is per account and explicit:
- `eth_getTransactionCount` at `latest` counts mined transactions only. At `pending` it adds the accepted public transactions with contiguous nonces.
- `eth_sendRawTransaction` parses with real `Transaction.from`, then, with the text a real node returns: wrong chain ID is rejected with `invalid chain id for signer`; a nonce below the mined count is rejected with `nonce too low`; a nonce already held by a public pending transaction replaces it only if both fee fields are at least 10 percent higher, otherwise it is rejected with `replacement transaction underpriced`, and a successful replacement marks the old hash `replaced`. A nonce above the next pending one is parked as queued and is not mined until the gap fills, because a real node's pool holds it; a scenario may opt into rejection with `setFutureNoncePolicy('reject')`, which returns `nonce too high`.
- A relay acceptance (`eth_sendBundle` or the bloXroute route) records its signed transactions as `accepted` on route `bundle` or `bloxroute` against their target block and changes neither count. Only `mine` can include one.
- `mine({ include?, exclude? })` includes the named hashes in nonce order, or by default every eligible public pending transaction, leaving out any hash named in `exclude` for this block only. When several accepted transactions compete for one nonce, the first included wins and the others are `dropped`. Mining advances `latest` and creates the receipt and block entries, and `eth_getTransactionReceipt` is a valid `null` until then. `neverMine(hash)` keeps a hash out of every block while later blocks still mine.

Every transition appends to `history` in order.

Tests to add to `harness.test.ts`, each naming the AC. The first is the tracer: a real ethers `Wallet` signs and sends one public transaction through a real provider on the fake transport; `latest` is unchanged and `pending` has risen; after `mine` the real `tx.wait()` resolves with the real receipt and `latest` has risen. Then: a transaction with the wrong chain ID, and one with a nonce too low, are refused with the real text and do not grow `node.submitted`; a same-nonce replacement below the bump is refused with the real text and one above it marks the old hash `replaced`; a relay acceptance leaves both counts unchanged; `mine({ include: [first] })` with two competing hashes shows `first` `mined` and the other `dropped`, with a receipt only for `first`; a hash under `neverMine` keeps a `null` receipt while `node.mine()` advances later blocks; a future nonce stays queued until the gap fills, and under `setFutureNoncePolicy('reject')` is refused with `nonce too high`.
