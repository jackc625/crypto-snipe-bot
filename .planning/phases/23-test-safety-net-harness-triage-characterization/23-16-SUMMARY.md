## AUD-ANTIRUG-018: the Setup Answer and What the Code Says

**Operator's answer:** "4. ANTIRUG-018: that command you sent me only output \"eth ETH_WS_URL set\"". So ENABLED_CHAINS is eth only (or unset, which defaults to eth), and ETH_WS_URL has a non-empty value. I did not read `.env`; the operator ran the check.

**Exposure on this setup, from the code:** the bot never starts the HTTP anti-rug poller that AUD-ANTIRUG-018 is about.
- `chainRegistry.ts:644` parses ENABLED_CHAINS with the same `eth` default and trimming as the command, and `chainRegistry.ts:662` sets `wsRpcUrl = process.env.ETH_WS_URL || null`, the same truthiness the command printed.
- `createChainContext` (`chainRegistry.ts:1066`) calls `getWsProvider`, which returns null only for an empty URL (`provider.ts:33-40`).
- `startChainAntiRugListener` takes the HTTP branch (`startHttpPollingAntiRug`, `detector.ts:1224`) only when `ctx.wsProvider` is falsy (`detector.ts:590-603`).
- Every later reassignment of `ctx.wsProvider` stores a newly built `WebSocketProvider`, never null:
  - the anti-rug reconnect (`detector.ts:923-929`);
  - both DEX reconnect loops (`bot.ts:1563-1564`, `bot.ts:1605-1606`);
  - the dashboard Start callback (`bot.ts:1814-1818`, which takes the `getWsProvider` branch because the URL is set).
- No path falls back to HTTP polling after a WebSocket failure or a refused reconnect.

AUD-ANTIRUG-018 becomes reachable as soon as a chain without a WebSocket address is enabled. Its DEX-listener sibling AUD-BUY-036 follows the same rule (`bot.ts:1530-1533`). The WebSocket path has its own confirmed outage findings, and these **do** apply to this setup: AUD-ANTIRUG-005 (backfill does not replay a real outage after a long healthy session) and AUD-ANTIRUG-002 (a refused reconnect kills the process). The S1 grade (ESC-ANTIRUG-03) stands, per the operator's earlier ruling and the standing instruction.
